# Как наряд появляется и доходит до человека: ручное создание, регион, загрузка, бригада

Дата: 2026-11-27. Часть N-3-б реестра. Раздел ТЗ — §48 «Наряды и задачи»,
строки «Наряд создаётся вручную или автоматически по аварии оборудования» и
«Назначение инженеру или бригаде с учётом региона и загрузки; маршрут к
объекту». Критерий US-48: «Наряд приходит в течение минуты, с адресом,
описанием аварии и нужными запчастями».

N-3-а закрыла вторую половину той же строки — что инженер делает на объекте.
Здесь закрывается первая: откуда наряд берётся и как находит исполнителя.

## Что есть до начала работы

1. **Автоматическое создание есть, ручного нет.** `createWorkOrder` вызывают
   ровно две ветки: `openWorkOrdersForAlerts` по аварии §30 и перевод заявки
   §51 в наряд. Ни страницы, ни метода `POST /v1/work-orders` не существует,
   хотя §50 его перечисляет. Планового обслуживания и монтажа, то есть двух
   типов из четырёх в §48, завести нельзя вообще: они ни из какой аварии не
   рождаются.
2. **Назначение есть, но слепое.** `assignWorkOrder` проверяет сеть и право
   `workorders.write` — и это всё. Панель наряда печатает плоский список
   сотрудников в алфавитном порядке. Ни региона, ни загрузки в коде нет ни
   слова: `Employee` не знает, где человек работает, а сколько у него открытых
   нарядов никто не считает. Диспетчер выбирает фамилию наугад.
3. **Бригады не существует.** `WorkOrder.assigneeId` — один `Employee`.
   «Назначение инженеру **или бригаде**» выразить нечем. При этом §49 уже
   говорит «машина бригады», и `Warehouse.kind = VAN` с хранителем-инженером
   есть — то есть фургон бригады в базе есть, а бригады нет.
4. **Диспетчер — роль без рабочего места.** В `BUILT_IN_ROLES` есть
   `DISPATCHER` с правами `workorders.read` и `workorders.write`, но ни одной
   страницы, сделанной для него: `/me/work-orders` — список «моих» нарядов
   глазами исполнителя. Тот же случай, что `tickets.write` до N-1 и
   `warehouse.write` до US-49.
5. **Маршрут к объекту есть.** `MapsDeepLink` в панели наряда и на телефоне.
   Эта строка §48 уже закрыта, здесь её не трогаем.

## Решения

### Регион — это город, а не новая сущность

Сущности «регион» в базе нет, и заводить её незачем: у пункта есть `city`, у
склада есть `city`, у заявки §51 адрес печатается городом. Поэтому регион
инженера — список городов: `Employee.regions String[]`.

Соглашение то же, что у `pointIds` рядом: **пусто значит вся сеть**. Так новый
сотрудник сразу виден диспетчеру, а не выпадает из подбора до тех пор, пока
кто-то не вспомнит про поле.

Наряд объекта генерации в подборе не участвует вообще. §47 — это сеть зарядных
пунктов: `assignWorkOrder` уже требует `order.operatorId`, у компании-
производителя сотрудников нет. Значит и город берётся всегда у пункта, и
`Asset.address` разбирать не нужно.

### Загрузка — число открытых нарядов, и она честная для бригады

`openLoad(employee)` — сколько у человека открытых нарядов (`NEW`, `ASSIGNED`,
`EN_ROUTE`, `IN_PROGRESS`, `WAITING_PART`, `DONE`), считая и личные, и наряды
его бригад. Бригадный наряд — это работа того же человека, и не считать его
значит обещать диспетчеру свободного инженера, у которого на сегодня четыре
выезда с бригадой.

Загрузка бригады — **максимум** по её людям, а не сумма и не среднее. Бригада
едет вместе, поэтому занята настолько, насколько занят самый занятый в ней.

### Порядок подбора — три ступени, и чужой город не исключается

`suggestAssignees(workOrderId)` возвращает кандидатов (инженеров и бригады
одним списком) в порядке:

1. город пункта есть в списке кандидата — точное совпадение;
2. у кандидата список пуст — вся сеть;
3. у кандидата другие города.

Внутри ступени — по загрузке возрастанию, затем по имени. Третья ступень не
выбрасывается: в три часа ночи кто-то всё равно должен поехать, и диспетчер
должен видеть, что выбор есть, но он не по региону. Рядом с каждым кандидатом
печатается причина: город, «вся сеть» или «другой регион», и число открытых
нарядов.

Кандидатом человек становится только с правом `workorders.write` и только
если область его пунктов (`pointIds`) допускает этот пункт — то есть `can()`
из §47, а не отдельная проверка.

### Бригада — своя таблица, назначение исключающее

```prisma
model Crew {
  id         String
  operatorId String          // бригада принадлежит сети
  name       String
  regions    String[]        // пусто — вся сеть, как у инженера
  members    CrewMember[]
  workOrders WorkOrder[]
  @@unique([operatorId, name])
}

model CrewMember {
  crewId     String
  employeeId String
  lead       Boolean @default(false)  // старший: ему письмо адресовано, остальным — копия
  @@unique([crewId, employeeId])
}
```

`WorkOrder.crewId String?` рядом с `assigneeId`. Назначено ровно одно из двух:
`assignWorkOrder` ставит одно и **обнуляет** другое. Два исполнителя у наряда
— это ничей наряд.

Человек может быть в нескольких бригадах: в жизни инженер утром едет с одной
бригадой на монтаж, днём один по жалобе.

### Право работать в наряде бригады

`work-order-access.ts` — единственное место, где этот вопрос решается, и
добавляется там одна ветка: участник назначенной бригады работает в наряде так
же, как личный исполнитель, независимо от того, что ему потом урезали в
области пунктов. Правило то же, что уже записано для исполнителя: наряд ему
уже назначили.

Списки — `/me/work-orders` и `readEngineerOrders` для телефона — получают то же
условие: наряды моей бригады мои.

### Письмо бригаде

`notifyPendingWorkOrders` сегодня адресует письмо исполнителю, а если его нет
— владельцу сети. Добавляется средняя ступень: наряд назначен бригаде —
письмо уходит каждому её участнику с подтверждённой почтой. Если ни у кого
почта не подтверждена, работает прежняя ветка владельца: наряд, о котором
никто не узнал, хуже наряда, о котором узнал владелец.

### Автоматическое назначение по аварии — чтобы минута US-48 была правдой

Наряд, родившийся из аварии или из заявки клиента, никто не назначает: сегодня
он остаётся `NEW`, и письмо уходит владельцу сети. Критерий US-48 — «наряд
приходит в течение минуты» **инженеру**, а не владельцу, и ночью диспетчера
нет.

Поэтому `createWorkOrder` получает `autoAssign?: boolean`, и две
автоматические ветки его включают: сразу после создания спрашивается
`suggestAssignees`, и первый кандидат назначается. В журнале это
`workorder.assigned` с актором `system` и причиной подбора, так что утром
видно, кто решил и почему. Кандидатов нет — наряд остаётся `NEW` и письмо
идёт владельцу, как сегодня.

Ручное создание диспетчером **не** назначает само: диспетчер стоит рядом и
выбирает. Форма просто подставляет первого кандидата в поле.

## Рабочее место диспетчера

`/me/charger-operator/[id]/dispatch` — то, чего у роли `DISPATCHER` не было.

- **Очередь**: открытые наряды сети, по приоритету и возрасту. На строке —
  пункт и город, тип, приоритет, статус, исполнитель (человек или бригада, с
  пометкой какой) и возраст. Неназначенные — первыми и помечены.
- **Назначить** прямо из строки: список кандидатов в порядке подбора, у
  каждого причина и загрузка. Назначение переводит `NEW → ASSIGNED` тем же
  `assignWorkOrder`, что и панель наряда.
- **Создать наряд**: тип (монтаж, обслуживание, ремонт, проверка), приоритет,
  пункт сети, заголовок, описание, что привезти, чек-лист из шаблона типа.
  Право — `workorders.write`. Описание пустым не бывает: наряд, по которому
  нечего делать, не наряд (правило уже в `createWorkOrder`).
- **Загрузка людей**: короткая таблица — инженер или бригада, регионы,
  открытых нарядов. Диспетчеру это нужно до того, как он откроет наряд.

Бригады и регионы живут на существующей странице `/staff`: это про людей и их
охват, а не про наряды. Там же — состав бригады и старший.

## Методы §50

- `GET /v1/work-orders?operatorId=…` — очередь, с исполнителем и загрузкой.
- `POST /v1/work-orders` — ручное создание. Денег и энергии не двигает,
  поэтому `Idempotency-Key` не требуется — то же решение, что у
  `POST /v1/pipeline`.
- `POST /v1/work-orders/[id]/assign` — `{ employeeId }` или `{ crewId }`,
  ровно одно. Отвечает назначенным исполнителем.
- `GET /v1/work-orders/[id]/candidates` — подбор, чтобы телефон и внешний
  диспетчер видели тот же порядок, что страница.

Чужая сеть во всех четырёх — 404, а не 403.

## Модули

- `src/lib/work/assignment.ts` — новый. `openLoad`, `suggestAssignees`,
  `autoAssign`. Ничего не пишет, кроме `autoAssign`, который вызывает
  существующий `assignWorkOrder`.
- `src/lib/work/crew-service.ts` — новый. Создать бригаду, состав, регионы,
  старший. Право `staff.write`, как у сотрудников §47.
- `src/lib/work/work-order-service.ts` — `assignWorkOrder` принимает бригаду,
  `createWorkOrder` принимает `autoAssign`, `notifyPendingWorkOrders` знает
  бригаду. Файл уже 342 строки; подбор в него не переезжает именно поэтому.
- `src/lib/work/work-order-access.ts` — ветка участника бригады.
- `src/lib/warehouse/engineer-view.ts` — наряды бригады в списке телефона.

## Проверка

Юнит-тесты:

- `assignment.test.ts` — загрузка считает бригадные наряды; максимум по
  бригаде, а не сумма; три ступени порядка; пустой список регионов — вся сеть;
  кандидат без `workorders.write` не кандидат; кандидат вне области пунктов не
  кандидат; наряд без пункта (объект генерации) — кандидатов нет.
- `crew-service.test.ts` — бригада чужой сети, участник из чужой сети,
  человек в двух бригадах, снятие последнего участника.
- `work-order-service.test.ts` — назначение бригаде обнуляет человека и
  наоборот; авария назначает сама и пишет актора `system`; нет кандидатов —
  наряд остаётся `NEW`.
- `work-order-access.test.ts` — участник бригады работает в наряде; участник
  другой бригады получает 404.

e2e `dispatch.spec.ts` на живой сборке: диспетчер открывает рабочее место,
создаёт наряд на пункт, видит подбор с загрузкой, назначает бригаду, наряд
появляется у участника бригады на `/me/work-orders` и на телефоне
`/{locale}/app/work-orders`.

## Чего здесь нет

- Push инженеру — `pushOpen()` закрыт, ключей APNs и FCM нет (US-29, M6).
- Маршрут между несколькими нарядами («маршрут дня», оптимизация объезда).
  §48 просит «маршрут к объекту», и он есть ссылкой в карты.
- Внутренний чат команды и чат по наряду — это N-4, следующий прогон.
