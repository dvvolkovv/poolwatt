# Кабинет производителя: листинг, объекты, токены

Блок A реестра ТЗ: US-01, US-03 (кабинетная половина), US-05.
Разделы ТЗ: §4, §5, §9 «Веб-кабинет производителя», §12, §14, §15.

## Задача

Сейчас пройти листинг можно только через REST. Производитель — человек, а не
скрипт, поэтому ему нужны страницы. Без листинга компания не получает
APPROVED, объекты не выходят из DRAFT, токены не выпускаются: это узкое место
всей платформы.

## Что строим

### 1. `/me/listing` — список компаний пользователя

Для каждой компании: название, страна, тип, статус KYB, статус последней
заявки, число объектов. Кнопка «Зарегистрировать компанию» открывает форму
реквизитов (§4: реквизиты, страна, лицензии).

Регистрация компании сразу создаёт черновик заявки (§14 «черновик»), чтобы
документы было куда грузить.

### 2. `/me/listing/[companyId]` — заявка на листинг

- Реквизиты компании (редактируются, пока заявка не отправлена).
- Документы: загрузка файлов PDF/JPEG/PNG до 20 МБ (US-01). Список уже
  загруженных со ссылкой на скачивание и кнопкой «удалить» (только в
  черновике).
- Кнопка «Отправить на проверку» → статус SUBMITTED, письмо оператору.
- После решения: статус, комментарий оператора, дата.

### 3. Хранение документов

Это KYB-документы, их нельзя класть в `/public`.

- Файлы на диске: `LISTING_DOCS_DIR` (по умолчанию `<cwd>/var/listing-docs`),
  путь `<applicationId>/<docId>.<ext>`.
- Отдаёт `GET /api/v1/listing-applications/[id]/documents/[docId]` — только
  владелец компании и ADMIN. Поток с диска, `Content-Disposition: inline`.
- В колонке `ListingApplication.documents` (Json) остаётся прежняя форма
  `{ name, url, bytes, mime }`, у загруженных добавляется `docId`. Миграции
  нет: админка и REST уже читают эту форму.
- Тип определяется по первым байтам (`%PDF`, `FF D8 FF`, `89 50 4E 47`), а не
  по заголовку из браузера: заголовок подделывается.
- Лимит тела серверных действий поднимаем до 24 МБ — по умолчанию в Next 1 МБ,
  иначе 20-мегабайтный PDF не дойдёт.

### 4. Уведомление оператора (US-01)

`src/lib/resend-listing.ts`:
- `sendListingSubmittedToAdmin` → `ADMIN_EMAIL`, тема с названием компании и
  страной, ссылка на `/admin/listings/<id>`.
- `sendListingDecisionToOwner` → владельцу на его языке: одобрено или
  отклонено с комментарием, ссылка на заявку.

Письма не должны валить форму: ошибка отправки пишется в лог, действие
считается успешным (так же сделано в `resend-build-request.ts`).

### 5. `/me/listing/[companyId]/assets` — объекты и мониторинг (US-03)

- Форма нового объекта: тип генерации, название, мощность, ёмкость
  накопителя, адрес, зона, номер счётчика, ссылка на гарантию происхождения.
- По объекту: статус (§14), дата активации, срок чистой телеметрии.
- API-ключ: выдача (ключ показывается один раз), список ключей с префиксом и
  датой последнего использования, отзыв.
- Таблица последних показаний: интервал, кВт·ч, статус валидации, примечание,
  выпущено ли. Это и есть «первые показания видны в кабинете» — страница
  читает `MeterReading` напрямую, лага нет.
- Правила продажи (§30): минимальная цена, доли «на рынок / в накопитель /
  себе». Нужны для US-28, здесь появляются бесплатно.

### 6. `/me/listing/[companyId]/tokens` — дашборд токенов (US-05)

- Выбор объекта и периода (7 / 30 / 90 дней или свои даты).
- Итоги: выпущено, доступно, продано, хранится, передано агрегатору, сожжено.
- Таблица партий: интервал, кВт·ч, статус, ссылка на гарантию происхождения.
- Кнопка CSV ведёт на существующий
  `GET /v1/assets/{id}/tokens?format=csv`.

## Чего в этой нарезке нет

- MQTT-приём (§4) — нужен брокер на сервере, отдельный кусок US-03.
- KYB и санкционный скрининг (US-02) — внешний провайдер, вопрос владельцу.

## Проверка

- Юнит: валидация загрузки (размер, тип по байтам, пустой список), создание
  компании вместе с черновиком заявки, отправка заявки из черновика.
- Интеграционные (на `poolwatt_test`): полный путь компания → документ →
  отправка → решение оператора; доступ к файлу чужим пользователем = 403.
- e2e: производитель регистрирует компанию, грузит PDF, отправляет, видит
  «на проверке».
