# Блок E — навигатор и карточка пункта

Дата: 2026-11-24. Истории: US-23 (§31), US-24 (§31).
Опирается на §27 (навигатор), §28 (поля карточки), §29 (мастер и жизненный
цикл), §15 (API и подпись оборудования), §4 (модерация оператором).

## Что уже есть и чего не хватает

Сверка кода с критериями дала неприятный, но ясный ответ: **пунктов приёма в
базе нет вообще**. Навигатор `/navigator` рисует точки, которые на лету
тянутся из OpenStreetMap (`src/lib/overpass-chargers.ts`), плюс заглушки из
`src/lib/chargers-mock.ts`. Кабинет оператора зарядок управляет только
карточкой бренда и одной ценой на всю сеть — завести пункт там негде.

| История | Чего не хватает |
| --- | --- |
| US-23 | фильтра «свободен сейчас» — занятости разъёма нет нигде; фильтры живут в состоянии React и не попадают в адрес, поэтому отфильтрованный вид нельзя ни сохранить, ни открыть повторно; с мини-карточки нельзя построить маршрут в один тап на телефоне (кнопка ведёт только в Google Maps) и нельзя перейти на полную карточку |
| US-24 | мастера нет; нет сущности пункта, обязательных полей §28, предпросмотра, модерации и статусов §29 |

Решение: завести пункты приёма как настоящую сущность, оставив слой OSM на
месте. OSM — это чужие станции на карте, наши пункты — это те, за которые
кто-то отвечает: у них есть владелец, тарифы, подключение и занятость.

## Модель данных (§28, §31)

Имена взяты из §31 («Дополнения к модели данных»).

**`AcceptancePoint`** — сам пункт. Владелец (`ChargerOperator`), тип
(`CHARGING_STATION`, `POWERBANK`, `GENERATION`, `MIXED`), адрес, координаты,
зона сети (`GridZone`), описание «как найти», источник энергии и гарантия
происхождения, ёмкость накопителя, часы работы (структурно: `open24`,
расписание по дням, праздники, временное закрытие), способы оплаты,
удобства, видимость (`PUBLIC`, `COOP_MEMBERS`, `OWN_CLIENTS`), бренд
(логотип, цвет значка, описание), подключение (версия OCPP, идентификатор
счётчика) и статус §29.

Статусы ровно те, что в §29: `DRAFT → REVIEW → TEST → PUBLISHED → SUSPENDED`.
Такой же набор уже есть у объектов генерации (`AssetStatus`), и это хорошо:
один жизненный цикл на две сущности, которые проходят одну и ту же проверку.

**`PointConnector`** — разъём: тип (`CCS2`, `CHADEMO`, `TYPE2`, `TYPE1`,
`TESLA`, `GB_T`, `SCHUKO`), мощность кВт, переменный или постоянный ток,
количество и **занятость**: `FREE`, `BUSY`, `OUT_OF_SERVICE`, `UNKNOWN`.

**`PointTariff`** — цена кВт·ч в токенах и в деньгах, окно по времени суток,
плата за простой, скидка члену кооператива. Несколько строк на пункт: §28
требует «цену по времени суток», а это и есть несколько окон.

**`PointPhoto`** — до десяти фотографий, файлы лежат вне `public`, отдаются
по ключу, как документы листинга.

**`PointApiKey`** — ключ оборудования пункта: тот же приём, что у объектов
генерации (`AssetApiKey`), с секретом подписи HMAC (§15). Им пункт сообщает
занятость разъёмов.

## US-24 — мастер карточки

Критерии: все обязательные поля проверяются; предпросмотр; отправка на
модерацию.

Семь шагов §29.1 по адресу
`/me/charger-operator/[operatorId]/points/[pointId]`:
тип → адрес → оборудование → тарифы → оплата → подключение → публикация.

- **Черновик сохраняется сам.** Шаг уходит на сервер при переходе к
  следующему и по кнопке «сохранить»; строка пункта создаётся сразу при входе
  в мастер со статусом `DRAFT`, поэтому закрытая вкладка ничего не теряет.
- **Проверка обязательных полей — по шагам.** Каждый шаг проверяет только свои
  поля, перейти вперёд с незаполненным обязательным нельзя. Отдельная функция
  `missingRequiredFields(point)` собирает всё, чего не хватает для отправки, и
  последний шаг показывает этот список: «отправить» недоступно, пока он не
  пуст. Одна функция и для шага, и для отправки — иначе мастер и сервер
  разойдутся в том, что считать заполненным.
- **Предпросмотр.** Справа — та же мини-карточка, какой пункт будет в
  навигаторе, из тех же данных и тем же компонентом. Не картинка и не макет:
  общий компонент `PointMiniCard`.
- **Отправка на модерацию** переводит в `REVIEW` и пишет оператору письмо, как
  у листинга (§4). Оператор одобряет на `/admin/points/[id]` — пункт переходит
  в `TEST`; в `PUBLISHED` он попадает сам, когда оборудование впервые
  сообщило занятость (§29.4 «после проверки оператором и первых данных от
  оборудования»).
- **§29.5.** Тарифы и часы работы владелец меняет без повторной модерации;
  изменение адреса или оборудования у опубликованного пункта возвращает его в
  `REVIEW`.

Шаблоны на сеть пунктов (§29.6) — это US-25, P1, и в этот блок не входит.

## US-23 — водитель ищет пункт

Критерии: фильтр по разъёму и доступности; результат за 2 секунды; маршрут в
один тап.

- **Занятость.** Наши пункты отдают занятость разъёмов, OSM-станции — нет, и
  честно показываются как «неизвестно». Фильтр «свободен сейчас» оставляет
  пункты, у которых есть хотя бы один разъём `FREE`; станции с неизвестной
  занятостью он прячет, потому что водитель просил свободный, а не «может
  быть».
- **Занятость приходит от оборудования.** `POST /v1/points/{id}/availability`
  с ключом пункта и подписью HMAC (§15), тело — состояние каждого разъёма.
  Первое же сообщение публикует пункт из `TEST`. Протокола OCPP мы не
  реализуем: станции разговаривают с нами по этому методу, а мост OCPP — это
  интеграция с конкретной сетью и вопрос владельца.
- **Фильтры в адресе.** `?connector=`, `?power=`, `?status=`, `?free=1`,
  `?q=` попадают в строку адреса и читаются при загрузке. Отфильтрованный вид
  становится ссылкой — без этого «нашёл и отправил другу» невозможно, да и
  проверить время ответа нечем.
- **Две секунды.** Наши пункты отдаются из базы запросом по прямоугольнику с
  индексом по координатам и статусу; измеряется и записывается в реестр.
  Медленный путь — внешний OSM, он уже кешируется на диск и не ухудшается.
- **Маршрут в один тап.** Кнопка маршрута переезжает в мини-карточку и
  работает как `MapsDeepLink`: на iPhone открывает Apple Maps, на Android —
  штатный навигатор, на остальном — Google Maps. Один тап, без выбора.
  Там же появляется ссылка на полную карточку — сейчас с мини-карточки на неё
  не перейти вообще.
- **Полная карточка.** `/c/[id]` учится показывать наши пункты: сейчас он
  ищет только в заглушках и на живой станции отдаёт 404.

## Порядок проверки

Юнит-тесты (против `poolwatt_test`):

- `point-service.test.ts` — создание черновика, сохранение шага, список
  недостающих обязательных полей по §28, отправка только при полном наборе,
  решение оператора, публикация первым сообщением о занятости, возврат в
  `REVIEW` при смене адреса и отсутствие возврата при смене тарифа.
- `point-availability.test.ts` — приём занятости по ключу с подписью, отказ
  без подписи и с чужим ключом, неизвестная занятость по умолчанию.
- `point-search.test.ts` — выборка по прямоугольнику, фильтр по разъёму,
  фильтр «свободен сейчас», невидимость черновиков и приостановленных.

e2e на живой сборке:

- `point-wizard.spec.ts` — владелец проходит мастер, видит предпросмотр,
  не может отправить с пустым обязательным полем, отправляет, оператор
  одобряет, пункт появляется в навигаторе после первого сообщения о занятости.
- `navigator-filters.spec.ts` — фильтр по разъёму и «свободен сейчас»
  сохраняются в адресе и переживают перезагрузку; маршрут строится в один тап;
  с мини-карточки открывается полная карточка.

## Чего эта работа не делает

- Мост OCPP к существующим сетям зарядок (нужен договор с сетью — вопрос
  владельца, он уже в реестре).
- Шаблоны на сеть пунктов (US-25, P1).
- Бронирование слота (§27, это блок G).
- Кластеризацию маркеров на мелком масштабе (§27) — отдельная работа по карте,
  к критериям US-23 она не относится.
