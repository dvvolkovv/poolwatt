# Маркетинговый модуль партнёра и подарочные кВт·ч — §41–§45

Дата: 2026-11-25. Блок I реестра. Истории US-40, US-41, US-42, US-43
(US-44 — P1, уходит в блок L).

## Что уже есть и на что опираемся

- Партнёр — это `ChargerOperator`, его забрал себе человек (`claimedById`),
  кабинет `/me/charger-operator/[id]`. Пункты — `AcceptancePoint` с модерацией
  оператором Poolwatt (`/admin/points`, `point-service.decidePoint`).
- Документы листинга лежат вне веб-корня (`var/listing-docs`) и отдаются
  маршрутом с проверкой доступа, тип берётся из первых байт файла
  (`src/lib/exchange/listing-docs.ts`). Медиа кампаний делаются по тому же
  образцу.
- Чек §46 уже умеет печатать строку подарка: `receipt-document.ts` читает
  `kwhFromGift` из разбивки и прячет строку при нуле.
- Оплата зарядки — `payment-service.chargeSession`, водопад §16.6
  (баланс → биржа → агрегатор) живёт отдельной чистой функцией
  `charge.planCharge`.

### Дыра, которую приходится закрыть здесь же

`Payment` имеет `pointId` и `connectorId`, но `chargeSession` их не заполняет:
их ставят только тесты. Поэтому настоящая зарядка не знает, в чьей сети она
прошла — а без этого US-41 («первая зарядка в моей сети») и US-43 («в чужой
сети подарок не применяется») невыразимы, и чек §46 печатается без бренда
сети. `chargeSession` получает `pointId`, `connectorId`, `startedAt`, `endedAt`,
маршрут `POST /v1/payments/charge` — тоже.

## Часть 1. Контент карточки (US-40)

### Модель

```
model MarketingContent {
  id, operatorId, pointIds String[]      // пусто = вся сеть партнёра
  type        MarketingContentType        // BANNER VIDEO GALLERY PROMO NEWS LINK
  title, body Text?, linkUrl String?
  placements  String[]                    // FULL_CARD NAVIGATOR_MINI CHARGE_COMPLETE PUSH
  audience    MarketingAudience           // ALL NEWCOMERS REGULARS COOP_MEMBERS CARD_HOLDERS
  zoneId?, radiusKm?                      // таргетинг по зоне и радиусу
  startsAt?, endsAt?, weekdays Int[], hourFrom Int?, hourTo Int?
  status      MarketingStatus             // DRAFT REVIEW APPROVED REJECTED
  submittedAt?, reviewedAt?, reviewedById?, reviewNote?
}

model MarketingAsset {
  id, contentId, storageKey @unique, contentType, sizeBytes, durationMs Int?, position
}
```

`MarketingAsset` повторяет форму `PointPhoto`: сам файл на диске, в базе —
только то, чем он является.

### Файлы

`src/lib/marketing/media-storage.ts`, каталог `var/marketing-media`
(`MARKETING_MEDIA_DIR`). Тип — из первых байт: JPEG, PNG, WebP, MP4.
Ограничения: картинка до 5 МБ, видео до 50 МБ и **до 60 секунд** (§41).

Длительность читается из самого контейнера: в MP4 есть коробка `mvhd` с
полями `duration` и `timescale`. `src/lib/marketing/mp4-duration.ts` —
маленький разбор дерева коробок, без зависимостей (ffprobe на сервере нет).
Видео, в котором `mvhd` не нашёлся, не принимается: мы не можем проверить
его длину, а значит не можем обещать §41.

Отдаёт файл `GET /api/v1/marketing/media/[assetId]`: всем, когда контент
одобрен и сейчас в своём расписании; владельцу сети и оператору Poolwatt —
всегда (это и есть предпросмотр до модерации).

### Расписание и выбор — чистая функция

`src/lib/marketing/visibility.ts`:

- `isContentLive(content, now)` — одобрен, попадает в `startsAt…endsAt`,
  день недели разрешён, час внутри `[hourFrom, hourTo)`. Окно, у которого
  `hourFrom > hourTo`, переходит полночь.
- `matchesAudience(content, viewer)` — `ALL` всегда; `NEWCOMERS` — ни одной
  захваченной оплаты в этой сети; `REGULARS` — три и больше; `COOP_MEMBERS` —
  действующее членство; `CARD_HOLDERS` **никогда**: карт Poolwatt не
  существует, и показывать акцию держателям несуществующих карт — обман.
  Это помечено в коде и в реестре.
- `selectForPlacement(contents, placement, now, viewer)` — что показать в
  одном месте, баннеры первыми.

Факты о зрителе собирает `readViewerFacts(userId, operatorId)`; для гостя
зритель — новичок.

### Где показывается

| Место | Что |
| --- | --- |
| `/c/[id]` — полная карточка | баннер, видео, галерея, акция, новость, ссылка |
| навигатор, мини-карточка | только баннер (§41) |
| `/me/wallet/receipts/[id]` — экран завершения зарядки | контент `CHARGE_COMPLETE` сети того пункта |
| push | за закрытым `pushOpen()` |

В CarPlay и Android Auto — ничего (§41), и это не наша забота: интеграции с
машиной ещё нет.

### Страницы

- `/me/charger-operator/[id]/marketing` — список контента со статусами,
  форма: тип, текст, ссылка, файлы, место показа, аудитория, расписание,
  пункты. Кнопки «предпросмотр» и «отправить на модерацию». Отказ показывает
  причину, контент возвращается в черновик и правится.
- `/admin/marketing` — очередь `REVIEW`, решение с запиской, письмо владельцу
  сети (`point-mail` как образец).

### API

`POST /v1/partners/{id}/content` (multipart) — то, что перечисляет §45.
Браузерная форма ходит через серверное действие, но и то и другое вызывает
один сервис `marketing/content-service.ts`.

## Часть 2. Подарочные кВт·ч (US-41, US-42, US-43)

### Чем подарок является

Подарок — **не токены в кошельке водителя**. Это запись о праве получить N
кВт·ч в сети партнёра. Отсюда само собой выполняется §43: подарок нельзя
перевести, продать на бирже и вывести в деньги, потому что его нет в
`Wallet.kwhBalance` и за ним не стоит ни одной партии.

Энергия всё равно откуда-то берётся. Берётся она у партнёра: при списании
подарка партии жгутся из **кошелька, которым кампания финансируется** — это
кошелёк человека, забравшего сеть себе, в зоне кампании. Партнёр отдаёт свою
выработку, водитель не платит. Сумма сошлась, ничего не выдумано.

Если в кошельке партнёра не хватает партий, подарок на непокрытую часть не
применяется, кампания встаёт на паузу с причиной, а водитель платит как
обычно. Это честный исход, и он проверяется тестом.

### Модель

```
model Campaign {
  id, operatorId, name
  trigger  CampaignTrigger    // FIRST_CHARGE NTH_CHARGE VOLUME_PERIOD
  triggerN Int?, triggerPeriodDays Int?
  giftKwh  Decimal
  scopePointIds String[]      // пусто = вся сеть
  validityDays Int
  oncePerClient Boolean @default(true)
  minNextChargeKwh Decimal?
  budgetKwh Decimal
  issuedKwh Decimal @default(0)
  fundingSource CampaignFunding  // TOKENS | FIAT (FIAT за закрытым переключателем)
  zoneId
  status CampaignStatus       // DRAFT ACTIVE PAUSED EXHAUSTED ENDED
  pauseReason?, startsAt?, endsAt?
}

model PromoGrant {
  id, campaignId, userId, operatorId
  amountKwh, usedKwh @default(0)
  expiresAt, status PromoGrantStatus   // ACTIVE USED EXPIRED REVOKED
  issuedAt, lastUsedAt?, notifiedAt?
  @@unique([campaignId, userId])       // «один раз на клиента» — правилом базы
}
```

Из таблицы §42 сейчас делается подарок «N кВт·ч». Скидка в процентах и
бесплатная бронь — отдельная история, и в реестре это сказано прямо, а не
заведено мёртвыми полями. Триггеры «регистрация по промокоду» и «день
рождения» тоже не делаются: у `User` нет даты рождения, а промокод — это
отдельный экран с вводом кода.

«Бюджет в деньгах» и финансирование с расчётного счёта закрыты
переключателем `campaignFiatFundingOpen()`: счёта партнёру выдаёт EMI,
которого нет, а пополнить денежный баланс сейчас нельзя (US-07). Открывает
только владелец.

### Начисление

`src/lib/marketing/campaign-engine.ts`, `awardAfterCharge(paymentId)`:

1. У оплаты есть `pointId` → сеть и пункт известны. Нет — выходим: подарок
   без сети невозможен.
2. Активные кампании этой сети, в чьей области лежит пункт, в своём окне дат.
3. Триггер: первая зарядка в сети / N-ная / объём за период — всё считается
   по захваченным оплатам в пунктах этой сети.
4. Бюджет: `issuedKwh + giftKwh <= budgetKwh`, иначе кампания становится
   `EXHAUSTED` и подарок не выдаётся.
5. Создаётся `PromoGrant` со сроком `validityDays`, `issuedKwh` растёт,
   пишется `AuditLog`. Всё в одной транзакции; второй заход по той же оплате
   ничего не добавляет.
6. Клиенту уходит письмо; push — за закрытым `pushOpen()`.

«В течение минуты» делается так же, как доставка чека: попытка сразу после
захвата оплаты, плюс `Payment.campaignsEvaluatedAt` и проход воркера раз в
минуту по оплатам, где это поле пусто. Медленная почта не держит ответ на
зарядку, а потерять начисление нельзя.

### Списание (US-43)

`planCharge` получает нулевой шаг: `giftKwh` — сколько подарочных кВт·ч
доступно именно в этом пункте, уже отобранных по сроку (раньше истекает —
раньше тратится). Порядок становится: **подарок → баланс → биржа →
агрегатор** (§43 «списывается первым, раньше обычного баланса»).

Сервис передаёт туда подарки только тогда, когда `pointId` принадлежит сети
подарка и области кампании. Зарядка в чужой сети и зарядка без пункта
получают ноль — это и есть критерий US-43, и на него идёт отдельный тест.

В транзакции захвата: партии на подарочную часть жгутся из кошелька
партнёра, `PromoGrant.usedKwh` растёт, исчерпанный подарок становится
`USED`, в разбивку чека попадает `kwhFromGift` и название сети. Одновременные
две зарядки одним подарком разбираются блокировкой строки подарка
(`FOR UPDATE`), как это сделано для книги заявок.

### Сгорание

Проход воркера: `ACTIVE` с истёкшим сроком → `EXPIRED`, неиспользованный
остаток возвращается в бюджет кампании (`issuedKwh -= остаток`, §43), и
кампания, стоявшая `EXHAUSTED`, может снова стать `ACTIVE`. `AuditLog` на
каждое сгорание.

### Страницы

- `/me/charger-operator/[id]/campaigns` — конструктор подарка: триггер,
  размер, область, срок, ограничения, бюджет, источник. Список кампаний с
  выданным, использованным и сгоревшим объёмом.
- `/me/gifts` (и блок «Подарки» в кошельке) — US-42: партнёр, остаток, срок,
  кнопка «Показать станции» → навигатор, отфильтрованный по этой сети.
- `GET /v1/wallets/me/gifts` — то, что перечисляет §45.

## Проверка

Разбор MP4, расписание, аудитория и выбор места — чистые функции, на них
обычные тесты. Начисление, списание и сгорание — тесты против `poolwatt_test`,
включая: зарядка в чужой сети подарка не тратит; подарок не попал в
`kwhBalance` и не продаётся заявкой; бюджет кончился — кампания встала;
сгоревший остаток вернулся; две одновременные зарядки одним подарком не
потратили его дважды. Живая сборка: загрузка баннера, модерация, показ в
карточке по расписанию, подарок за первую зарядку, трата в своей сети и
отказ в чужой.

## Что остаётся владельцу

1. Ключи APNs и FCM — push в US-40 (рассылка клиентам сети) и в US-41
   (уведомление о подарке). Пока обе доходят письмом.
2. Текст правил контента и запрета вводящей в заблуждение рекламы (§41):
   это юридический документ, его пишет не разработчик.
3. EMI и процессинг — бюджет кампании в деньгах и финансирование с
   расчётного счёта (§42). До тех пор кампании финансируются выработкой.
