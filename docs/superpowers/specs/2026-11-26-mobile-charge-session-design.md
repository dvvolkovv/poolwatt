# Мобильное приложение, этап M3-а: зарядка по QR

Дата: 2026-11-26. Разделы ТЗ: §8 (сценарий оплаты), §16.6 (водопад оплаты),
§22.9 (экран «Зарядка и навигатор»), §27 (кнопка «Зарядиться»), §32.5 (бронь
засчитывается в зарядку), §34, §46 (чек), §51 (сообщение о поломке).
Истории: US-20 (P0, не начата), US-08 (частично), US-30/US-31 в той части,
где бронь закрывается зарядкой.

Этап M3 из `2026-11-25-mobile-app-design.md` разделён на два прогона:
**M3-а — зарядка** (этот документ) и **M3-б — навигатор** (карта §27 с
кластеризацией, полные фильтры §27, карточка §28 под телефон, отзывы,
история доступности, маршрут во внешний навигатор, продление брони с
телефона). Разделение — потому что это две независимые работы с разными
доказательствами, а один прогон их обе не вмещает.

## Что есть и чего не хватает

Есть всё, кроме самого сеанса.

`quoteCharge` и `chargeSession` (`src/lib/exchange/payment-service.ts`)
выполняют водопад §16.6 целиком: подарок §43, баланс кВт·ч, роуминг §8,
покупка на бирже, агрегатор §16.7, комиссия по плану партнёра §53, чек §46,
кэшбэк US-12, запись в AuditLog, идемпотентность. `planCharge`
(`src/lib/exchange/charge.ts`) считает и сумму авторизации с запасом Y %.

Чего нет:

1. **Ни одной страницы, с которой человек начинает зарядку.** `chargeSession`
   вызывают только `POST /v1/payments/charge` и страница роуминга. То есть
   US-08 «частично», а US-20 «не начата» ровно потому, что водителю некуда
   нажать.
2. **Сеанса как состояния.** `chargeSession` — одно неделимое действие:
   «вот столько кВт·ч, посчитай и спиши». §16.6 же описывает два момента:
   «сумма авторизуется с запасом Y %» в начале и «списывается по факту» в
   конце. Между ними — зарядка, и её ход водитель должен видеть.
3. **Брони, которая закрывается зарядкой.** В `ReservationStatus` есть
   `FULFILLED`, и ни одна строка кода её не ставит: бронь сейчас может только
   истечь, быть отменённой или стать неявкой. §32.5 требует обратного — по
   приезду зарядка закрывает бронь, плата засчитывается, гарантия
   освобождается.

## Решение: сеанс как состояние, расчёт по факту

Появляется `ChargeSession` — запись о том, что водитель начал зарядку в
конкретном разъёме конкретного пункта. Жизненный путь:

```
            POST /v1/charge-sessions            отчёт оборудования
   (QR) ─────────────────────────────▶ AUTHORIZED ───────────────▶ ACTIVE
                                           │                        │
                                 отмена до  │                        │ отчёт «закончено»
                                 первого кВт│                        │ или «Завершить»
                                           ▼                        ▼
                                      CANCELLED                 COMPLETED
                                           ▲                        │
                 нет отчётов N минут ──────┴── EXPIRED              └─▶ Payment + Receipt §46
```

- `AUTHORIZED` — водитель подтвердил расчёт. Деньги под сеанс зарезервированы
  (`Wallet.reservedFiat`, тот же механизм, что держит средства под заявкой на
  покупку), разъём помечен `BUSY`, бронь водителя на этом разъёме переведена в
  `FULFILLED`.
- `ACTIVE` — пришёл первый отчёт о выданных кВт·ч.
- `COMPLETED` — расчёт: `chargeSession` по фактически выданным кВт·ч. Отсюда
  `Payment`, чек §46 и кэшбэк — всё существующим кодом.
- `EXPIRED` — оборудование не отчиталось ни разу за `CHARGE_SESSION_TTL_MIN`
  минут. Резерв снимается, разъём освобождается, денег не берут.

**Почему расчёт по факту, а не по резерву кВт·ч.** Водопад §16.6 пересчитывается
заново в момент расчёта — против настоящего баланса, настоящей книги и
настоящей цены. Это буквально «списывается по факту». Резервировать ещё и
кВт·ч означало бы добавить `Wallet.reservedKwh` и научить уважать его перевод,
продажу, роуминг и сам расчёт — четыре места, которые сегодня работают и
покрыты тестами. Запас Y % на деньгах существует как раз для того, чтобы
расхождение цены между расчётом и фактом не ломало сеанс.

**Чего мы не делаем и почему.** Команду «начни зарядку» оборудованию мы не
отправляем: для этого нужен OCPP-мост к настоящей сети зарядок, которого нет
(вопрос владельцу открыт). Поэтому поток ровно такой же, как у телеметрии и
занятости разъёмов: **оборудование само отчитывается, мы никогда не
командуем**. Переключатель `ocppOpen()` в `src/lib/exchange/gates.ts` закрыт
по умолчанию; за ним — `RemoteStartTransaction` и `RemoteStopTransaction`. Пока
он закрыт, кнопка «Завершить» на экране зарядки говорит водителю отсоединить
кабель и ждёт финального отчёта станции, а не делает вид, что остановила её.

## Модель данных

Две новые таблицы, ни одна существующая колонка не меняется.

```prisma
model ChargeSession {
  id             String   @id @default(cuid())
  userId         String
  walletId       String
  zoneId         String
  pointId        String
  connectorId    String
  reservationId  String?  @unique   // §32.5 — какую бронь закрыл сеанс
  status         ChargeSessionStatus @default(AUTHORIZED)
  plannedKwh     Decimal  @db.Decimal(18, 3)
  deliveredKwh   Decimal  @default(0) @db.Decimal(18, 3)
  authorizedFiat Decimal  @default(0) @db.Decimal(18, 2)
  currency       String   @default("EUR")
  quote          Json     @default("{}")  // снимок ChargePlan на момент согласия
  tariffVersion  Int?
  paymentId      String?  @unique
  idempotencyKey String?  @unique
  createdAt      DateTime @default(now())
  startedAt      DateTime?
  lastMeterAt    DateTime?
  endedAt        DateTime?
  closeReason    String?
}

model ChargeSessionTick {
  id        String   @id @default(cuid())
  sessionId String
  at        DateTime @default(now())
  kwhTotal  Decimal  @db.Decimal(18, 3)
  powerKw   Decimal? @db.Decimal(8, 2)
}
```

`ChargeSessionTick` — не украшение: по нему рисуется ход зарядки и по нему же
разбирается спор «мне списали больше, чем я взял». Счётчик только растёт:
отчёт с меньшим `kwhTotal`, чем предыдущий, отклоняется.

## Сервис

`src/lib/exchange/charge-session.ts`:

| Функция | Что делает |
| --- | --- |
| `authorizeSession(args)` | Проверки в одной транзакции под блокировкой разъёма: пункт опубликован, разъём свободен или забронирован этим же водителем, у водителя нет другого живого сеанса, расчёт §16.6 посчитан, денег на запас хватает. Резервирует деньги, помечает разъём `BUSY`, закрывает бронь §32.5, пишет AuditLog. `Idempotency-Key` обязателен. |
| `reportMeter(args)` | Ключ пункта + HMAC §15, как у занятости. Пишет тик, двигает `deliveredKwh`, при первом отчёте переводит в `ACTIVE`, публикует событие. Монотонность и окно ±300 с. |
| `finishSession(args)` | Расчёт: `chargeSession` по факту внутри той же транзакции, что снимает резерв и освобождает разъём. Идемпотентно по `sessionId`: два одновременных «закончено» дают один `Payment`. |
| `expireStaleSessions(now)` | Сеансы без единого отчёта дольше TTL — в `EXPIRED`, резерв снять, разъём освободить. Вызывается воркером раз в минуту. |
| `readActiveSession(userId)` | Что показать на экране зарядки. |
| `resolveQrCode(code)` | Разбор кода: `PW1:<pointId>:<connectorId>`, либо адрес `…/app/charge?p=&c=`, либо один `pointId`. Чужой код — честная ошибка «это не код Poolwatt». |

Плата за бронь при `feeCountsTowards` вычитается из стоимости сеанса в момент
расчёта и печатается в чеке отдельной строкой §46.

## API

| Метод | Кто вызывает | Замечание |
| --- | --- | --- |
| `POST /v1/charge-sessions` | приложение | `Idempotency-Key` обязателен |
| `GET /v1/charge-sessions/me/active` | приложение | |
| `POST /v1/charge-sessions/{id}/meter` | оборудование | Bearer ключа пункта + HMAC §15 |
| `POST /v1/charge-sessions/{id}/stop` | приложение или оборудование | `reason` |
| `GET /v1/points/resolve?code=` | приложение | что зашито в QR |

## Живой канал

Новых каналов не добавляем: события сеанса публикуются в существующий
`wallet.{userId}` типами `charge.started`, `charge.tick`, `charge.completed`.
Телефон на экране зарядки подписывается тем же `useChannel`, что экран
кошелька, и билет на канал уже выдаётся его владельцу.

## Экраны

**`/{locale}/app/charge`** — вкладка «Зарядка».

- Живой сеанс есть → крупная цифра выданных кВт·ч, мощность, время, стоимость
  по текущему водопаду, разъём и пункт, кнопки «Завершить» и «Сообщить о
  проблеме» (§51).
- Живого сеанса нет → кнопка «Сканировать QR» (камера через `getUserMedia` +
  `jsqr`, без нативного плагина), поле «ввести код» для случая, когда камеры
  нет, и список ближайших пунктов по геолокации (существующий `searchPoints`)
  с расстоянием и ценой.

**`/{locale}/app/charge/start?p=&c=`** — расчёт до подтверждения (§54 «клиент
видит итоговую цену и все платы до подтверждения»): пункт, разъём, сколько
кВт·ч брать, разбивка §16.6 построчно (подарок, баланс, роуминг, биржа,
агрегатор, комиссия), сумма авторизации с запасом, зачёт платы за бронь,
кнопка «Начать зарядку» со своим ключом идемпотентности.

**`/{locale}/app/charge/[id]`** — завершённый сеанс: итог и ссылка на чек
`/app/wallet/receipts/[id]`, который уже есть.

Печать QR для оборудования — страница оператора
`/me/charger-operator/[id]/points/[pointId]/qr`: по одному коду на разъём,
`qrcode` уже в зависимостях.

## Что проверяется

- Юнит: разбор QR, монотонность счётчика, переходы состояний, расчёт по факту
  при упавшем и выросшем балансе, зачёт платы за бронь, истечение сеанса.
- Одновременность: два `POST /v1/charge-sessions` с одним ключом → один сеанс;
  два «закончено» одновременно → один `Payment`; два водителя на один
  свободный разъём → один сеанс, второму отказ.
- Playwright на Pixel 7 против живой сборки: ввод кода разъёма → расчёт →
  подтверждение → подписанный отчёт оборудования → цифра на экране выросла →
  завершение → чек открывается из ленты кошелька.
- APK со сборочной полосы; `android-build` добавляет в манифест разрешение
  камеры. iOS нужен `NSCameraUsageDescription` в `Info.plist` — отдельная
  правка в репозитории на Маке и сборка TestFlight.

## Чего в этапе нет и почему

- Команда станции по OCPP — за `ocppOpen()`, нужен мост к настоящей сети.
- Оплата картой (US-08 целиком) — нужен процессинг; деньги идут с денежного
  баланса кошелька.
- Push «зарядка закончена» — нужны ключи APNs/FCM, этап M6.
- Карта §27 с кластеризацией и фильтрами, карточка §28 под телефон, отзывы и
  история доступности — этап M3-б.

## Вопросы владельцу

1. **TTL сеанса без отчётов.** Предложение: 15 минут — столько же, сколько
   `waitMinutes` по умолчанию держится бронь.
2. **Потолок на сеанс.** Водитель выбирает, сколько кВт·ч брать; предложение —
   шаги 10/20/50 кВт·ч и «сколько войдёт» с потолком по тому, что водопад
   может обеспечить. Без OCPP остановить станцию на потолке мы не можем,
   поэтому расчёт идёт по факту, даже если фактом оказалось больше.
3. **QR на станциях.** Код печатает оператор из своего кабинета. Если у сети
   уже есть свои QR, нужен их формат — иначе водитель будет сканировать чужой
   код и получать «это не код Poolwatt».
