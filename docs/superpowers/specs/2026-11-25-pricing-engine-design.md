# Тарифный движок — §52–54

Дата: 2026-11-25. Блок J реестра. Отдельных историй у блока нет, но на нём
стоят уже сделанные блоки G (бронь), H (чеки) и I (подарки).

## Что уже есть

Почти вся таблица §52 в системе есть — но врассыпную и без версий:

| §52 | Где живёт сейчас |
| --- | --- |
| Цены кВт·ч в деньгах и токенах по времени суток | `PointTariff` (окна по минутам суток), правится мастером пункта |
| Одна цена на всю сеть | `ChargerOperator.pricePerKwh`, кабинет и `POST /charger-operators/{id}/price` |
| Минимальная цена продажи и доли выработки | `Asset.minSalePrice`, `shareToMarketPct`, `reserveSocPct` — кабинет листинга |
| Плата за бронь, гарантия, штраф | `ReservationPolicy` |
| Плата за простой | `PointTariff.idleFeePerMin` |
| Скидка членам кооператива | `PointTariff.coopDiscount`, `ReservationPolicy.coopFree` |
| Кэшбэк и подарки | блок I (`Campaign`), кэшбэк — US-12, не начат |
| Комиссия субпартнёрам | нет |

Комиссия платформы — `FeePlan` (процент со сделки и с зарядки по типу
участника) и `src/lib/exchange/fees.ts`.

## Чего не хватает, по пунктам §53–54

1. **§54: «Любое изменение тарифа версионируется: новые сделки идут по новой
   версии, текущие брони и заявки — по старой.»** Ни одно из пяти мест не
   версионируется. Бронь свои числа копирует (`Reservation` — копия §33), и это
   единственное место, где правило уже соблюдается. Остальное правится на
   месте, истории нет, и **напечатанный чек меняется задним числом**:
   `receipt-document.ts` берёт тариф из живых строк `PointTariff`, поэтому
   партнёр, поправивший цену, перепишет цену за кВт·ч на чеках прошлого месяца.
   Это главная находка блока.
2. **§53: тарифные планы партнёров** — базовый, расширенный, корпоративный, с
   подпиской. `FeePlan` знает только два процента и тип участника.
3. **§53: плата за бронь в пользу платформы** — комиссии с брони нет вообще.
4. **§53: индивидуальные условия отдельным партнёрам** — переопределений нет.
5. **§52: комиссия субпартнёрам** (сеть с франчайзи) — нет.
6. **§53: карточные тарифы** — карт нет (§19 ждёт EMI), и выдумывать
   интерчейндж нельзя.
7. **§54: «Собственные предприятия Poolwatt без скрытых преимуществ.»**
   Выполняется, но ничем не проверено.
8. **§54: расчёт комиссий с отражением в бухгалтерии обеих сторон.** Выгрузка
   §46 показывает выручку партнёра; комиссии платформы в ней нет.

## Часть 1. Версии тарифов (§54, правило 2)

### Модель

```
model PricingRule {
  id         String
  scope      PricingScope   // POINT_TARIFF NETWORK_PRICE RESERVATION_POLICY
                            // SALE_RULES SUBPARTNER_FEE
  scopeId    String         // id пункта, сети, объекта
  operatorId String?        // сеть, когда правило её
  companyId  String?        // компания, когда правило объекта
  version    Int
  params     Json           // то, что человек задал, целиком
  activeFrom DateTime
  createdById String?
  note       String?
  @@unique([scope, scopeId, version])
}
```

`params` — снимок, а не ссылка. Через год строка `PointTariff` может быть
удалена вместе с пунктом, а чек за прошлый март всё равно должен печатать ту
цену, по которой был выставлен.

### Как пишется

Единственный писатель — `src/lib/pricing/pricing-service.ts`:

- `recordPricingChange({scope, scopeId, params, actorId, note}, tx)` —
  добавляет версию N+1 с `activeFrom = now`. Вызывается **в той же
  транзакции**, что и запись в живую таблицу: версия без изменения и
  изменение без версии одинаково бесполезны.
- `pricingAt(scope, scopeId, at)` — версия, действовавшая в этот момент.
- `readPricingHistory(scope, scopeId)` и `readNetworkPricing(operatorId)`.

Пять мест, которые начинают через него ходить: мастер пункта (тарифы),
политика брони, правила продажи объекта, цена сети в кабинете и то же через
`POST /charger-operators/{id}/price`.

### Как читается

`Payment` получает `tariffVersion Int?` — версия тарифа пункта на момент
начала сессии. `buildReceiptDocument` берёт тариф из этой версии, а к живым
строкам обращается только для старых оплат, где версии нет. Напечатанный чек
перестаёт меняться.

Заявки и сделки биржи версией тарифа не пользуются: они идут по книге, а не по
тарифу пункта, и уже хранят свою цену в `Trade.price`. Бронь свои числа
копирует и так; версия пишется ей в `pricingVersion` для истории.

### Что видит партнёр

`/me/charger-operator/[id]/pricing` — одна страница вместо четырёх разбросанных
форм: цена сети, тарифы каждого пункта, плата за бронь, правила продажи
объектов. Рядом с каждым числом — версия и дата, ниже — вся история: версия,
кто, когда, что изменилось. Править по-прежнему можно там же, где и раньше;
эта страница сводит и показывает историю.

`PUT /v1/partners/{id}/pricing` и `GET /v1/partners/{id}/pricing/history` —
методы, которые перечисляет §54.

### Сверка

Суточная сверка (§16.11) получает ещё одну проверку: живая таблица совпадает с
последней версией. Расхождение значит, что кто-то написал в таблицу мимо
сервиса, и это ошибка, которую надо увидеть, а не починить молча.

## Часть 2. Планы платформы (§53)

```
model PlatformFeePlan {
  id, name, tier PlanTier         // BASIC EXTENDED CORPORATE
  participantType CompanyType?
  tradeFeePct, chargeFeePct, bookingFeePct
  subscriptionFiat, subscriptionPeriod  // подписка §53
  includedInvoices Int?, includedCampaigns Int?   // бесплатный объём
  isDefault
}

model PartnerPlan {
  companyId? / operatorId?, planId
  overrides Json        // §53 «индивидуальные условия отдельным партнёрам»
  activeFrom
}
```

`FeePlan` остаётся как есть и становится представлением над планом: его два
процента уже читает `fees.ts`, и ломать расчёт комиссии ради переименования
незачем. Новая таблица добавляет уровень, подписку, плату с брони и
переопределения.

`/admin/fee-plans` — планы, кому назначен, переопределения.
`PUT /v1/admin/fee-plans/{id}` — метод из §54.

Карточные тарифы (выпуск, обслуживание, интерчейндж) заводятся полями за
закрытым `cardTariffsOpen()`: карт нет, ставки назначает EMI, и придуманный
интерчейндж — это неверный документ.

## Часть 3. Субпартнёры и правила §54

- **Комиссия субпартнёрам (§52).** `SubpartnerAgreement` между двумя сетями:
  процент, который головная сеть удерживает с зарядки у франчайзи. Считается
  вместе с комиссией платформы и попадает в бухгалтерию обеих сторон.
- **§54 правило 1.** Тест: компания, помеченная как собственная (`Company`
  Poolwatt), не получает ни лучшего места в навигаторе, ни приоритета в книге
  заявок при равной цене и времени.
- **§54 правило 3.** «Клиент видит итоговую цену и все платы до
  подтверждения» — `quoteCharge` это делает, бронь тоже; нужен тест, что в
  обоих ответах видны плата за простой и скидка кооператива.
- **§54 правило 4.** Выгрузка §46 получает строки комиссии платформы и
  комиссии головной сети — обе стороны видят одно и то же число.

## Проверка

Версии, разрешение «что действовало в момент T» и расчёт комиссий — чистые
функции и тесты против `poolwatt_test`. Главный тест блока: партнёр меняет цену,
и **чек, выписанный до изменения, печатает прежнюю цену**. Живая сборка: правка
цены, история версий, страница планов у оператора.

## Что остаётся владельцу

1. Цифры тарифных планов §53 — сколько стоит расширенный и корпоративный план,
   что входит в бесплатный объём. Это коммерческое решение, не наше.
2. Карточные тарифы и интерчейндж — EMI и процессинг.
3. Ставки комиссии с брони в пользу платформы.
