# Долги ядра биржи — проект

Дата: 2026-11-24. Блок B реестра выполнения. Шесть требований ТЗ, которые
ядро биржи объявляет, но не выполняет: ключ идемпотентности на всех POST
(§15), подпись HMAC для оборудования (§15), спотовая цена из внешнего рынка
(§6, §16.5), WebSocket-каналы (§15), нагрузочный тест матчинга (§17),
суточная сверка реестра токенов с данными сети (§16.11).

Каждая часть самостоятельна: своя миграция, свои тесты, свой коммит.
Порядок работ — порядок этого документа.

## 1. Ключ идемпотентности на всех POST

### Что есть

`idempotencyKey(req)` в `src/lib/exchange/api.ts` читает заголовок, но его
используют только три маршрута: `/v1/orders`, `/v1/payments/charge`,
`/v1/wallets/me/buy`. Защита построена на колонке `idempotencyKey @unique` в
таблицах `Order` и `Payment`: повторный ключ находит прежнюю запись и
возвращает её. Заголовок необязателен — без него повтор создаёт второй
ордер.

Не защищены: `/v1/wallets/me/transfer` (двигает энергию),
`/v1/telemetry/readings` (выпускает токены; спасает только уникальность
`(assetId, intervalStart)`), `/v1/accounts` (выпуск счёта).

### Решение

Общая таблица повторов плюс сохранение нынешних колонок.

```prisma
model IdempotencyRecord {
  id          String   @id @default(cuid())
  endpoint    String            // "POST /v1/orders"
  key         String            // значение заголовка
  userKey     String            // id пользователя или id ключа оборудования
  requestHash String            // SHA-256 канонизированного тела
  status      Int               // HTTP-код сохранённого ответа
  response    Json
  createdAt   DateTime @default(now())

  @@unique([endpoint, key])
  @@index([createdAt])
}
```

Обёртка `withIdempotency(req, endpoint, handler)`:

1. Нет заголовка — `400 Idempotency-Key header is required`. §15 требует
   ключ на всех POST, и все вызывающие стороны наши.
2. Есть запись с тем же `requestHash` — отдать сохранённый ответ как есть,
   с заголовком `Idempotency-Replayed: true`.
3. Есть запись с другим `requestHash` — `409 Idempotency-Key was already
   used with a different body`.
4. Нет записи — выполнить, затем записать ответ. Запись идёт отдельной
   транзакцией после успеха: ответы об ошибках не кешируются, повтор после
   сбоя должен иметь право попробовать снова.
5. Два одновременных запроса с одним ключом: второй падает на уникальном
   индексе `(endpoint, key)` при вставке «в работе» и получает
   `409 A request with this Idempotency-Key is in flight`. Первым шагом
   вставляется заглушка со `status = 0`, по завершении она обновляется
   настоящим ответом; заглушка старше 60 секунд считается брошенной и
   перехватывается.

Колонки `Order.idempotencyKey` и `Payment.idempotencyKey` остаются: это
второй рубеж внутри транзакции, он дешёвый и уже проверен тестами. У
`TokenTransfer` добавляется такая же колонка.

Срок хранения записей — 30 суток, чистит суточная задача воркера. Это не
финансовые данные §17 (сами ордера и платежи лежат вечно), а журнал
повторов.

### Где применяется

`POST /v1/orders`, `/v1/payments/charge`, `/v1/wallets/me/buy`,
`/v1/wallets/me/transfer`, `/v1/telemetry/readings`, `/v1/accounts`,
`/v1/coop/{id}/votes`. Запросы-расчёты (`/v1/payments/quote`,
`/v1/roaming/quote`) ничего не меняют и остаются без ключа.

Клиентская сторона: хелпер `postJson(url, body)` в `src/lib/api-client.ts`
подставляет `crypto.randomUUID()` и переиспользует его при повторной
отправке той же формы, иначе повтор по кнопке «ещё раз» снова пройдёт.

## 2. Подпись HMAC для оборудования

### Что есть

`AssetApiKey` хранит только `tokenHash` — SHA-256 открытого ключа. Проверка
подписи невозможна: сервер не знает секрета.

### Решение

У ключа появляется секрет подписи, хранимый в обратимом виде.

```prisma
// AssetApiKey
signingSecretEnc String?   // AES-256-GCM, ключ из API_KEY_ENC_KEY
signingSecretIv  String?
```

- При выдаче ключа генерируется 32-байтный секрет, показывается владельцу
  один раз рядом с ключом (как сейчас показывается сам ключ) и хранится
  зашифрованным. Без `API_KEY_ENC_KEY` в окружении выдача секрета
  невозможна — ключ выдаётся как сейчас, без подписи.
- Канонизированная строка: `v1.<timestamp>.<METHOD>.<path>.<sha256(body)>`.
  Заголовки: `X-Poolwatt-Timestamp` (секунды Unix) и
  `X-Poolwatt-Signature: v1=<hex>`.
- Окно допустимого времени — ±300 секунд. Повтор ловится таблицей
  идемпотентности из части 1, отдельного нонса не нужно.
- Переход: если у ключа есть секрет, подпись обязательна; если нет — запрос
  принимается без подписи. Так старые объекты продолжают работать, а новые
  сразу подписывают. Сводка по объектам, которые ещё не подписывают, видна
  в кабинете.
- MQTT: те же поля `ts` и `sig` внутри сообщения, канонизированная строка
  `v1.<ts>.MQTT.<topic>.<sha256(payload без sig)>`.

Шифрование — в новом `src/lib/crypto-box.ts`: `seal(plain)` и
`open(enc, iv)`, оба требуют 32-байтный ключ из `API_KEY_ENC_KEY`
(base64). Никаких других применений у модуля пока нет, но он нужен и для
будущих секретов EMI.

## 3. Спотовая цена из внешнего рынка

### Что есть

`GridZone.spotPrice` — константа, которую выставляет оператор руками.
Коридор §16.5 считается от неё, и пока её не обновляют, он защищает от
манипуляций вчерашней ценой.

### Решение

Источник цены становится свойством зоны.

```prisma
// GridZone
spotSource   String  @default("MANUAL")  // MANUAL | ENTSOE
spotAreaCode String?                     // EIC-код зоны ENTSO-E, напр. 10YLT-1001A0008Q

model ZoneSpotPrice {
  id            String   @id @default(cuid())
  zoneId        String
  intervalStart DateTime
  price         Decimal  @db.Decimal(12, 4)
  currency      String   @default("EUR")
  source        String
  fetchedAt     DateTime @default(now())

  @@unique([zoneId, intervalStart, source])
  @@index([zoneId, intervalStart])
}
```

- `src/lib/exchange/spot-entsoe.ts`: клиент публикации A44 («Day-ahead
  prices») ENTSO-E Transparency Platform. Разбор XML своими средствами —
  документ плоский, зависимость не нужна. Цена приходит в €/МВт·ч, в
  реестре хранится €/кВт·ч.
- `src/lib/exchange/spot-service.ts`: `refreshZoneSpot(zone)` берёт цены на
  сутки вперёд, пишет историю, выставляет `GridZone.spotPrice` ценой
  текущего интервала. Ошибка источника не трогает прежнюю цену и пишет
  предупреждение: лучше вчерашний ориентир, чем отсутствие коридора.
- Воркер: раз в час в 10 минут. Плюс выбор текущего интервала из истории
  каждые 5 минут вместе с закрытием интервала.
- Переключатель `spotFeedOpen()` в `gates.ts`, закрыт, пока владелец не
  даст токен ENTSO-E (`ENTSOE_TOKEN`). При закрытом переключателе зоны
  остаются `MANUAL`, код полностью покрыт тестами на записанном ответе
  (`src/lib/exchange/__fixtures__/entsoe-a44.xml`), сеть в тестах не
  трогается.

История цен нужна не только коридору: она же основание для §16.7 (нет
ликвидности — расчёт по внешней спотовой цене) и для отчётов.

## 4. WebSocket-каналы

### Что есть

Ничего. Кошелёк, книга заявок и пульт перечитывают страницу.

### Решение

Отдельный процесс и шина на Redis.

- `realtime/index.ts` — процесс `poolwatt-realtime` под PM2, сервер на
  пакете `ws`, слушает `127.0.0.1:3101`. nginx проксирует `/ws` с
  `Upgrade`.
- Каналы ТЗ §15: `orderbook.{zone}`, `trades.{zone}`, `wallet.{user}`,
  `telemetry.{asset}`.
- Авторизация: браузер не умеет ставить заголовки на WebSocket, поэтому
  `POST /v1/realtime/ticket` отдаёт подписанный HMAC-билет на 60 секунд со
  списком разрешённых каналов (свой кошелёк, свои объекты, книги заявок
  зон — публичны). Клиент подключается на `/ws?ticket=…`. Секрет билета —
  `NEXTAUTH_SECRET`, он уже есть на сервере.
- Публикация: `src/lib/exchange/realtime.ts` с `publish(channel, event)`
  поверх Redis `PUBLISH`. Вызовы — в `order-service` (после сделки),
  `wallet-service` (после изменения баланса), `telemetry-service` (после
  выпуска). Публикация никогда не роняет транзакцию: ошибка Redis только
  пишется в лог.
- Клиент: хук `useChannel(name)` в `src/hooks/use-channel.ts`,
  переподключение с возрастающей паузой, при отсутствии соединения
  страница продолжает работать на данных сервера. Первым потребителем
  становится `/me/wallet` (закрывает US-17), затем терминал.

Почему не SSE, который App Router умеет сам: ТЗ называет WebSocket-каналы и
двустороннюю подписку, а пульт станции (§30) потребует команд от клиента.

## 5. Нагрузочный тест матчинга

`scripts/load-matching.ts` против `poolwatt_test`:

1. Готовит зону, N кошельков с балансом и выпущенными токенами.
2. Гонит заявки заданной частотой, половина лимитных в книгу, половина
   рыночных.
3. Считает пропускную способность и задержки p50/p95/p99 исполнения
   рыночной заявки, печатает таблицу и выходит с кодом 1, если задержка
   p95 больше 100 мс.

Цель §17 — 5000 заявок в секунду на зону. Нынешний матчинг — одна
транзакция Postgres на заявку, столько он не даст. Задача этой части —
измерить и записать настоящие числа и узкое место в реестр, а не подогнать
результат. Оптимизация (книга заявок в памяти с журналом) — отдельный блок,
который будет опираться на эти измерения.

## 6. Суточная сверка реестра с данными сети

### Что есть

`reconcileWalletBalances()` сверяет баланс кошелька с суммой партий
токенов. Это внутренняя непротиворечивость, а §16.11 требует сверки с
данными сети.

### Решение

`src/lib/exchange/reconciliation-service.ts`, четыре проверки:

1. Баланс кошелька против суммы его партий (нынешняя проверка).
2. Каждое показание со статусом `valid` имеет ровно одну партию, и
   количество совпадает с точностью 0,001 кВт·ч.
3. Нет партий без показания (сирот) и нет двух партий на одно показание.
4. Сумма выпущенного по объекту за сутки против суммы показаний объекта за
   сутки.

Результат пишется в таблицу прогонов и в `AuditLog`, расхождение никогда не
исправляется само — это признак ошибки выше по течению.

```prisma
model ReconciliationRun {
  id          String   @id @default(cuid())
  startedAt   DateTime @default(now())
  finishedAt  DateTime?
  scope       String            // "daily"
  checks      Json              // по проверке: сколько сверено, сколько расхождений
  driftCount  Int      @default(0)
  ok          Boolean  @default(true)

  @@index([startedAt])
}
```

При расхождении оператору уходит письмо на `ADMIN_EMAIL` (через
`operator-email.ts`, который уже умеет падать на `EMAIL_REPLY_TO`).
Страница `/admin/reconciliation` показывает последние прогоны и их
расхождения: без страницы оператор о сверке не узнает.

Сверка с внешними данными оператора сети (DSO) — вопрос владельцу: нужен
договор и доступ к их выгрузке. До ответа «данные сети» для нас — показания
счётчиков объектов, подписанные ключом объекта.

## Проверка

- Юнит- и интеграционные тесты на бросовой базе `poolwatt_test` по каждому
  пункту, включая одновременные случаи (§6 CLAUDE.md): два POST с одним
  ключом, две сделки по одной партии.
- e2e: повтор отправки формы покупки не создаёт второй ордер; кошелёк
  обновляет баланс по WebSocket без перезагрузки.
- Нагрузочный прогон и сверка запускаются на сервере, их числа попадают в
  реестр выполнения.

## Чего ждём от владельца

- Токен ENTSO-E, первая торговая зона и её EIC-код; интервал 15 или 60
  минут (§18). До ответа часть 3 стоит за закрытым переключателем.
- Доступ к выгрузке оператора сети для полной сверки §16.11.
- `API_KEY_ENC_KEY` генерируется на сервере нами, участия владельца не
  требует.
