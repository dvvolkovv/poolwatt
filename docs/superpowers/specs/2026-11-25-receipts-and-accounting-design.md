# Чеки и бухгалтерия партнёра — проект

ТЗ §46, §50 (US-45, US-46). Дата: 2026-11-25.

## Что уже есть и чего не хватает

`Receipt` существует с первого дня биржи: его создаёт платёж за зарядку
(`payment-service.ts`), расчёт сделки (`order-service.ts`) и закрытие брони
по неявке (`reservation-service.ts`). В записи лежат объём, сумма, валюта,
перечень сожжённых партий и свободный `breakdown`. Страница
`/me/wallet/receipts/[id]` печатает эти поля списком.

Для §46 не хватает почти всего остального:

| §46 требует | Сейчас |
| --- | --- |
| логотип Poolwatt, логотип и реквизиты сети | нет: у `ChargerOperator` есть только `logoUrl`, реквизитов нет вовсе |
| пункт, разъём, начало и конец зарядки | нет: у `Payment` только свободная строка `chargePointId` |
| объём и источник энергии | объём есть, источника нет |
| цена в токенах и в деньгах | только в деньгах |
| плата за бронь и её зачёт | есть у чека неявки, нет у чека зарядки |
| разбивка: баланс, подарочные, карта | баланс есть, подарочных нет (блок I), карты нет (нет процессинга) |
| кэшбэк и бонусы | нет (US-12, P1) |
| НДС и налоговые реквизиты | нет |
| QR-код проверки | нет |
| доставка: пуш, кабинет, почта, печать | только кабинет |
| выбор способа доставки в настройках | нет |
| выгрузка месяца в DATEV, BMD, Excel, CSV, PDF | нет |

## Решения

### 1. Чек знает, где и когда была зарядка

`Payment` получает настоящие связи: `pointId`, `connectorId`, `startedAt`,
`endedAt`. Свободная строка `chargePointId` остаётся — это идентификатор
оборудования, который присылает станция, — но реквизиты сети, адрес пункта и
источник энергии чек берёт через `pointId`. Поля необязательные: зарядка на
стороннем пункте (роуминг, OSM-станция) чек всё равно выдаёт, просто без
брендирования.

### 2. Реквизиты и НДС вносит партнёр, а не мы

Юридический план ЕС прямо требует «налоговое заключение по НДС» по каждому
виду операции. Ставку НДС и налоговые реквизиты мы не придумываем: их вносит
партнёр в своём кабинете. Новая модель `OperatorAccounting` (одна на сеть):
юридическое название, рег. номер, номер НДС, адрес, ставка НДС, а также номера
счетов для DATEV и BMD. Пока ставка не заполнена, чек печатает «НДС не указан»
вместо цифры, а выгрузка в DATEV и BMD отказывается работать и говорит, чего
не хватает. Переключателя в `gates.ts` здесь нет: закрывать нечего — это не
внешняя сторона, а данные партнёра о себе.

### 3. Номер чека

`Receipt.number` вида `PW-2026-000123` из последовательности Postgres
(`receipt_number_seq`), и `Receipt.verifyCode` — 16 случайных байт для QR.
Номер наш собственный, а не номер налогового документа: нумерация счетов по
правилам страны — часть налогового заключения.

### 4. Состав чека считается в одном месте

`src/lib/receipts/receipt-document.ts` собирает из записи чека полный документ
§46: брендирование и реквизиты сети, пункт и разъём, окно зарядки, объём и
источник энергии, цену в деньгах и в токенах, плату за бронь и её зачёт,
разбивку оплаты, кэшбэк, строки НДС, адрес проверки для QR. Одна функция —
один документ; её читают страница кабинета, страница печати, письмо и выгрузка.

Строки, которых ещё нет в системе (подарочные кВт·ч — блок I, кэшбэк — US-12),
в структуре документа предусмотрены и не печатаются, пока равны нулю. Когда
блок I положит подарки в `breakdown`, строка появится сама.

### 5. Источник энергии — из партий, а не из вывески

Источник чек берёт у сожжённых партий: `EnergyToken` → `Asset.kind` и
`renewableSource`. Пункт со своей вывеской «солнце» может отдать
киловатт-час, выпущенный ветром; в чеке стоит то, что было сожжено. Если
партии не из нашего реестра (докуплено на бирже у другой зоны) — пишется
`смешанный`.

### 6. Доставка

`User` получает два флага: `receiptEmail` и `receiptPush`, оба включены —
«по умолчанию только электронный» из §46. Печать флага не требует: она
происходит по требованию на терминале.

`src/lib/receipts/receipt-delivery.ts` отправляет письмо (брендированный HTML
с логотипом сети) и пуш, когда `pushOpen()` открыт, и записывает в чек
`deliveredAt`, `deliveryChannels`, `deliveryError`. Платёжный путь зовёт её
после фиксации транзакции и никогда не падает из-за почты. Воркер раз в минуту
добирает чеки с пустым `deliveredAt` — это и есть гарантия критерия «чек
формируется в течение минуты».

Печать на терминале станции: `/me/wallet/receipts/[id]/print` — та же
страница без навигации, с правилами печати. Терминала у нас нет, браузер есть
у любого терминала.

### 7. QR-код

`/r/[code]` — открытая страница проверки без входа: номер чека, дата, пункт,
объём, сумма и слово «подлинный». Персональных данных нет: QR на бумажке видит
кто угодно. Код неугадываемый, поиск по нему — по уникальной колонке.
Сам QR рисуется на сервере в SVG (`qrcode`).

### 8. Выгрузка для бухгалтера

Право `finance.read` уже есть у встроенной роли `ACCOUNTANT` (§47), значит
бухгалтера приглашает владелец сети обычным порядком, а страница
`/me/charger-operator/[id]/accounting` показывает ему период, строки и пять
кнопок.

`src/lib/accounting/ledger.ts` превращает чеки сети за период в строки
проводок: дата, номер документа, пункт, кВт·ч, сумма, НДС, валюта, вид
операции, ссылка. В периметре — зарядки на пунктах сети и платы и штрафы по
броням. Сделки биржи и выплаты принадлежат компании-производителю, а не сети,
и в эту выгрузку не входят (отдельная история).

Пять форматов, каждый своим файлом в `src/lib/accounting/`:

- `csv` — точка с запятой и BOM, как ждёт Excel в ЕС;
- `xlsx` — `exceljs`, лист со строками и итогами;
- `pdf` — `pdfkit` со шрифтом DejaVu (в системе есть, иначе Helvetica);
- `datev` — EXTF Buchungsstapel, формат 700, с заголовочной строкой DATEV;
- `bmd` — CSV для BMD NTCS.

DATEV и BMD требуют номеров счетов (Berater, Mandant, счёт выручки,
контрсчёт). Без них выгрузка отказывает с понятным сообщением и ссылкой на
страницу реквизитов — выдумывать номера счетов нельзя, ошибка в проводке
стоит бухгалтеру дороже, чем отсутствие файла.

Выдача — `GET /api/v1/charger-operators/[id]/accounting/export?from&to&format`,
проверка прав через `can(employee, "finance.read")` либо владелец сети.

## Как проверяется

- `receipt-document.test.ts` — состав §46: реквизиты сети, НДС и «не указан»,
  цена в токенах, зачёт платы за бронь, источник из партий, скрытые нулевые
  строки, чужой чек.
- `receipt-delivery.test.ts` — настройки пользователя, закрытый пуш, запись
  каналов, ошибка почты не ломает платёж, добор воркером.
- `ledger.test.ts` — границы периода, только свои пункты, итоги.
- `accounting-export.test.ts` — заголовки и строки CSV, DATEV, BMD; xlsx
  читается обратно; PDF начинается с `%PDF`; отказ DATEV без счетов.
- e2e `receipts.spec.ts` на живой сборке — зарядка, чек с логотипом и QR,
  страница печати, открытая проверка по коду, скачивание всех пяти форматов
  бухгалтером.

## Чего эта работа не делает

- Пуш остаётся за `pushOpen()`: ключей APNs и FCM нет (US-29, US-45 — тот же
  переключатель). Письмо уходит всегда, поэтому критерий US-45 выполняется,
  но строку «в пуше» закрывает владелец ключами.
- Карта в разбивке оплаты: процессинга нет, деньги идут с денежного баланса
  кошелька (как в US-08). Строка в документе есть, значение — баланс.
- Подарочные кВт·ч и кэшбэк — блок I и US-12.
- Возврат ошибочного чека через поддержку с журналом изменений (§46) —
  отдельная история, в US-45 и US-46 её нет.
