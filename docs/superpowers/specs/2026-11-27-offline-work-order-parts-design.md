# Наряд в телефоне и списание запчасти без связи (US-49)

Дата: 2026-11-27. Разделы ТЗ: §48 («Наряды и задачи», строка «Офлайн-режим:
наряд закрывается без связи и синхронизируется позже»), §49 («Склад
запчастей», строки про машину бригады и про списание «по факту»), §47 (роли),
§15 (идемпотентность POST), §22 (оболочка телефона), §25 (офлайн).
Истории: US-49 (P1, частично) — «как инженер, хочу списать запчасть в наряде
без связи», критерий приёмки: «списание сохраняется офлайн и
синхронизируется». Попутно US-48 получает экран наряда в самом приложении, а
не только на мониторе.

Это первая незакрытая история в блоке L реестра, которая не ждёт владельца:
US-14 и US-15 ждут процессинга карт, US-38 и US-39 — автопроизводителя, этап
M6 — KYC, EMI и ключей push. Ждать US-49 больше нечего: оболочка §22,
сервис-воркер и офлайн-экран появились на этапе M1, и мобильное приложение,
которым эта история была заблокирована, существует с 2026-11-25.

## Что есть и чего не хватает

Серверная часть §49 готова целиком. `src/lib/warehouse/stock-service.ts`
выполняет все шесть операций склада одним правилом — «остаток есть сумма
движений», — заводит заявку US-50 в той же транзакции и считает
себестоимость по цене на момент движения. `POST /v1/stock-movements`
принимает все шесть видов. Наряды §48 есть в `work-order-service.ts` со
полной машиной статусов, письмом инженеру и автозаводом по аварии.

Не хватает четырёх вещей, и первая из них делает историю невыполнимой.

1. **Инженер не может тронуть склад вообще.** `requireNetwork` в
   `stock-service.ts` пускает только того, кто `claimedById` сети, то есть
   владельца. Право `warehouse.write` объявлено в `staff-service.ts` и входит
   в роли ENGINEER и STOREKEEPER, но его не проверяет ни одна строка кода:
   `grep warehouse.write src/` находит только объявление и тест, который
   проверяет, что оно в списке. То есть инженер, которому §49 поручает
   «бронирует и списывает их по факту», сегодня получает «This network
   belongs to somebody else». Это надо исправить раньше офлайна, иначе
   офлайн синхронизирует отказы.

2. **В приложении нет наряда.** US-48 закрыта страницей `/me/work-orders` на
   мониторе, и её собственный комментарий это признаёт: «The mobile app of
   §25 is still an open question, so „в приложении“ is this page today».
   Приложение §22 с тех пор появилось, а наряда в нём нет: ни таба, ни
   раздела в хабе, ни экрана.

3. **У `POST /v1/stock-movements` нет ключа идемпотентности.** Пока вызов
   делает рука на странице, это терпимо. Очередь, которая досылает, —
   это повтор по определению: оборвалась связь на ответе, и инженер списал
   плату дважды. §49 кладёт стоимость запчасти в себестоимость пункта, то
   есть движение склада двигает деньги, и правило §15 на него
   распространяется.

4. **Сервис-воркер умеет только GET.** `public/sw.js` сознательно мал:
   навигация с одним запасным экраном и кэш статики. Ни одной записи он не
   хранит и не досылает.

Попутно: движение склада не пишет `AuditLog`. Пишет только заявка US-50
(`stock.restock.raised`), а приход, списание и выдача на наряд — нет. Для
истории, где запись делается в офлайне чужими руками и досылается позже,
журнал — не украшение.

## Устройство

### 1. Кто имеет право (сервер)

`requireNetwork` заменяется на `requireStockActor(operatorId, userId, opts)`
в том же файле. Пускает:

- владельца сети (`claimedById`), как сегодня;
- сотрудника с правом `warehouse.write` — это ENGINEER и STOREKEEPER из
  восьми ролей §47;
- для выдачи на наряд (`ISSUE`) — ещё и назначенного исполнителя этого
  наряда, с учётом области видимости: `can(employee, "warehouse.write",
  order.pointId)`, то есть инженер, которому выдали два пункта, не спишет
  запчасть на наряд третьего.

Один `can()` решает и здесь, как во всём §47: проверка права, написанная в
двух местах, расходится, и расходится в сторону «да».

Для выдачи на наряд добавляется ещё одно условие, которого не было: склад,
с которого списывают, должен быть либо машиной этого инженера
(`Warehouse.keeperEmployeeId`), либо складом сети, а не чьей-то чужой
машиной. Поле в схеме уже есть и стоит пустым.

### 2. Идемпотентность и журнал

`POST /v1/stock-movements` уходит под существующий `idempotent()` из
`src/lib/exchange/api.ts`: `endpoint: "POST /v1/stock-movements"`,
`userKey` — идентификатор пользователя, ключ — из заголовка
`Idempotency-Key`, обязательного. Повтор возвращает тот же
`movement.id` и заголовок `Idempotency-Replayed`. Ключ придумывает
устройство в момент, когда инженер нажал кнопку, а не в момент отправки:
иначе два досыла одной записи — два разных ключа.

Каждое движение пишет `AuditLog` внутри своей транзакции —
`stock.movement.<kind>`, в `after` склад, запчасть, количество, наряд и
серийный номер.

### 3. Очередь на устройстве

`src/lib/mobile/offline-queue.ts` — чистый модуль над внедряемым
хранилищем (`Storage`), поэтому тесты не нуждаются в браузере:

```
enqueue(storage, op): QueuedOp      // придумывает id = ключ идемпотентности
list(storage): QueuedOp[]           // порядок — порядок нажатий
flush(storage, send): FlushReport   // отправляет по одной, сверху вниз
forget(storage, id): void           // инженер убирает отклонённую запись
```

Запись несёт вид операции, тело запроса, ключ идемпотентности, время
нажатия, состояние (`pending` | `rejected`) и причину отказа словами
сервера.

Два вида операций, оба из §48: `stock.issue` — выдача запчасти на наряд, и
`workorder.status` — перевод наряда по машине статусов, в том числе
закрытие. Вторая попала сюда потому, что §48 просит её тем же предложением
(«наряд закрывается без связи») и она ездит по той же дороге.

Разбор ответов — то, из-за чего очередь не бывает «простой»:

| Что вернулось | Что делает очередь |
| --- | --- |
| 2xx, в том числе повтор | запись удаляется, она исполнена |
| сеть не ответила | запись остаётся `pending`, попробуем позже |
| 409 «ещё выполняется» | остаётся `pending`: ответ будет, просто не сейчас |
| 4xx по существу (на полке нет, не ваш наряд) | становится `rejected` с причиной и остаётся на экране |
| 5xx | остаётся `pending` |

Запись не исчезает молча никогда. Инженер, который списал плату в подвале,
должен увидеть на экране, что она списана — или почему нет.

Досыл запускается в трёх случаях: экран наряда смонтировался, браузер
сказал `online`, инженер нажал «отправить сейчас». Никакого таймера:
Background Sync не годится, потому что `SyncManager` в WKWebView нет, а
оболочка iOS — это WKWebView; одна механика на обе платформы лучше двух.

Очередь живёт на странице, а не в сервис-воркере, по той же причине, по
которой §25 запретил кэшировать баланс: отказ надо показать человеку
словами, а у воркера нет экрана.

### 4. Снимок склада для офлайна

Чтобы выбрать запчасть без связи, её надо видеть. Экран наряда кладёт в
`localStorage` снимок «что у меня в машине и на ближайшем складе» — то, что
§49 просит показывать в наряде, — и печатает рядом время снимка, как это
делает офлайн-баланс §25. Количество в снимке — справка, а не истина:
решает сервер при досыле, и его отказ «на полке только два» виден как
`rejected`.

### 5. Экраны

- `/{locale}/app/work-orders` — мои наряды: заголовок, приоритет, статус,
  адрес. Список инженера, не владельца.
- `/{locale}/app/work-orders/[id]` — наряд: адрес и как найти, описание
  поломки, нужные запчасти, фотографии клиента, кнопки статуса §48,
  и «списать запчасть» — выбор из снимка, количество, серийный номер,
  примечание. Сверху — счётчик неотправленного, если он не нуль.
- Раздел `work` в хабе `/app/more` для того, кто сотрудник с правом
  `workorders.read`: `moreSections` получает четвёртый флаг.

Экран наряда кэшируется сервис-воркером как навигация — то есть при
отсутствии связи откроется запасной экран, а не наряд. Это осознанно: наряд
со вчерашним описанием хуже честного «нет связи». Офлайн нужен записи, а не
чтению; инженер открывает наряд, пока связь есть, и теряет её на месте
работ, не доходя до перезагрузки страницы.

## Испытания

Юнит-тесты:

- `offline-queue.test.ts` — порядок, ключ не меняется между досылами, пять
  строк таблицы разбора ответов, `forget`.
- `stock-access.test.ts` — владелец может; инженер с `warehouse.write`
  может; инженер с чужим пунктом не может; посторонний не может; чужая
  машина как склад не годится.
- `stock-service.test.ts` — дополнить: два одновременных списания последней
  платы, выживает одно.
- идемпотентность маршрута: тот же ключ дважды — одно движение, второй ответ
  помечен повтором; тот же ключ с другим телом — 409.

e2e на Pixel 7 против живого домена (`mobile-work-order.mobile.spec.ts`):
инженер открывает наряд, `context.setOffline(true)`, списывает плату, видит
её в неотправленном, `setOffline(false)`, видит, что ушла, и остаток на
складе упал на единицу. Второй случай: списание больше, чем есть на полке,
уходит в отказ со словами сервера и остаётся на экране.

## Чего в этой работе нет

- Чек-лист работ, подпись и фотографии «до и после» из §48 — это не US-49.
- Бронирование запчасти («бронирует и списывает» §49) — отдельная операция,
  которой нет в схеме; US-49 просит списание.
- Push о наряде — ждёт ключей APNs/FCM вместе с этапом M6.
