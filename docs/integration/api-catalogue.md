# Poolwatt — перечень API

Документ для внешних разработчиков, которые будут подключать Poolwatt к
внешней инфраструктуре: банку-эмитенту, провайдерам KYC/KYB, процессингу
карт, сетям зарядок, бирже спотовых цен, магазинам приложений и
автомобильным платформам.

Составлено 2026-11-28 сверкой с кодом (ветка `main`). Три части:

1. **API для фронтальных продуктов** — то, что вызывает любой наш клиент:
   сайт, телефон, а в будущем любой другой фронт.
2. **API для оборудования** — то, что вызывает железо: счётчик объекта
   генерации, зарядный пункт, касса сети.
3. **API внешних поставщиков** — то, что нам нужно получить снаружи, и то,
   что мы обязаны выставить наружу навстречу. Это и есть задание для
   подключающей стороны.

Ссылки вида «§19», «US-13» — номера разделов и пользовательских историй
технического задания. Сам текст ТЗ в этот документ не переносится.

## Часть 0. Общие правила

**Базовый адрес.** `https://poolwatt.com/api` — боевой. Версия в пути:
`/api/v1/...`. Два метода вне версии (`/api/producers`, `/api/chargers`)
обслуживают лендинг и в счёт API не идут.

**Формат.** JSON в обе стороны, UTF-8. Успех — `{ "ok": true, ... }` или
прямой объект данных; ошибка — `{ "ok": false, "error": "<текст>" }` с
кодом 400 / 401 / 403 / 404 / 409 / 503. Валидация тела — zod, ошибка
приходит с кодом 400 и указанием поля.

**Закрытая возможность — это 503, а не 400.** Функции, которым нужна
внешняя сторона, стоят за переключателями в `src/lib/exchange/gates.ts`.
Закрытая отвечает `503` с текстом, чего не хватает. Это не ошибка клиента
и не повод повторять запрос.

**Идемпотентность (§15).** Любой POST, который двигает деньги или
киловатт-часы, требует заголовок `Idempotency-Key` (до 190 символов,
придумывает клиент). Повтор с тем же ключом возвращает **тот самый
ответ**, а не делает второе движение. Ключ привязан к паре «метод +
пользователь», поэтому один ключ у двух разных методов — две разные
записи. Запросы, которые ничего не двигают (расчёт цены, создание черновика
контента, заявка в поддержку), ключа не требуют — и это сознательное
решение, а не недоделка.

**Числа.** Киловатт-часы — три знака после запятой, цена — четыре.
Передаются числами JSON, не строками.

**Время.** ISO-8601 в UTC с `Z`. Интервалы рынка — начало интервала
(`intervalStart`).

### Аутентификация — главное место, которое придётся доделать

Сейчас у клиентского API **один** способ входа: cookie-сессия Auth.js
(`sessionUser()` в `src/lib/exchange/api.ts`). Так работают и сайт, и
мобильные приложения — потому что оба приложения это оболочка Capacitor
над живым сайтом, то есть внутри них настоящий браузер со своими cookie.

Любой фронт, который **не** браузер (нативный клиент, десктоп, терминал,
встроенная система автомобиля, чужая интеграция), так войти не может. Ему
нужен токен доступа. Этого в коде нет, и это первая задача для
подключающей стороны:

- выпуск токена по логину/паролю и по Taler ID (OIDC уже подключён,
  `src/lib/talerid/`);
- короткоживущий access-токен + refresh;
- `Authorization: Bearer <token>` рядом с cookie-сессией во всех методах
  `/v1/*`, где сейчас только `sessionUser()`;
- отзыв токена при отвязке устройства (`DELETE /v1/device-keys/{id}`).

Схема прав, которая уже есть и на которую токен должен лечь:

| Кто                | Как узнаётся                             | Чем ограничен                                                                       |
| ------------------ | ---------------------------------------- | ----------------------------------------------------------------------------------- |
| Пользователь       | сессия                                   | только свои кошелёк, сеансы, заявки, чеки                                           |
| Оператор платформы | сессия, `role = ADMIN`                   | решения по листингу, зоны, тарифы платформы                                         |
| Сотрудник сети     | сессия + роль §47                        | права `tickets.read`, `finance.read`, `warehouse.write` и область видимости пунктов |
| Объект генерации   | `Authorization: Bearer <ключ объекта>`   | только свои показания                                                               |
| Зарядный пункт     | ключ пункта + подпись HMAC               | только свои разъёмы и сеансы                                                        |
| Касса сети         | `Authorization: Bearer <ключ оператора>` | только цена своей сети                                                              |

### 1.18 Чего в API нет — только серверные действия

**Это самое важное для нового фронтального продукта.** В коде 50 файлов
серверных действий Next.js (`"use server"`) против 79 методов `/v1`. Всё,
что делает человек в кабинете, но чего нет в таблицах выше, существует
**только** как серверное действие, то есть вызывается из нашей же
React-страницы и больше ниоткуда. Браузерный фронт (и обе мобильные
оболочки, потому что внутри них браузер) этим пользуется. Нативный клиент
или фронт на другом стеке — не сможет.

Области, у которых есть страница, но нет метода API:

- регистрация, вход, восстановление пароля, настройки, привязка Taler ID;
- кабинет сети зарядок целиком: пункты, мастер создания пункта, штат §47,
  шаблоны, кампании, склад, диспетчер, бухгалтерия;
- кабинет производителя: правила продажи §30, панель виджетов §30/§31,
  заявки на строительство;
- кабинет подрядчика и заявки к нему;
- кооператив: голосование (чтение есть, голос — действие);
- бронирование пункта и жалоба на пункт;
- админка: зоны, сверка, тарифные планы, претензии по чекам, модерация
  контента, подрядчики, роуминговые коридоры;
- избранное, подарки, заявка на владение объектом.

Вывод для планирования: **любой новый фронтальный продукт, который не
браузер, требует сначала вынести нужные ему действия в `/v1`.** Объём —
примерно 60–90 новых методов, если выносить всё; меньше, если продукт
покрывает одну роль. Это работа, которую можно делать параллельно с
подключением внешних поставщиков, и она от поставщиков не зависит.

## Часть 2. API для оборудования

Железо не ходит по cookie. Два способа входа.

### 2.1 Ключ объекта генерации — счётчик, инвертор, шлюз

`POST /v1/telemetry/readings`

- `Authorization: Bearer <ключ объекта>` — ключ выдаётся в
  `POST /v1/assets/{id}/keys`, в открытом виде показывается один раз,
  хранится только SHA-256. **Личность объекта берётся из ключа, не из
  тела** — подменить объект в теле нельзя.
- `Idempotency-Key` обязателен.
- Пачка — до 1000 интервалов за запрос.
- Тело: `{ "readings": [ { "intervalStart": "...Z", "energyKwh": 4.125 } ] }`.
- Счётчик только растёт; повтор интервала не удваивает выпуск токенов.

Альтернативный транспорт — MQTT: тема
`poolwatt/v1/assets/<assetId>/readings`, ключ внутри сообщения. Брокер
сейчас слушает только `127.0.0.1` — наружу его выставлять нельзя без TLS
на 8883 и отдельных учётных данных на объект (см. 3.12).

### 2.2 Ключ пункта плюс подпись — зарядный пункт

Два метода, оба с подписью HMAC:

- `POST /v1/points/{id}/availability` — занятость разъёмов (§27, §29.4).
  Первый принятый отчёт публикует карточку пункта.
- `POST /v1/charge-sessions/{id}/meter` — сколько кВт·ч уже выдано.
  Чей это сеанс, решает принадлежность ключа пункту сеанса, а не заголовок.

Подпись (`src/lib/exchange/equipment-signature.ts`):

```
X-Poolwatt-Timestamp: <unix seconds>
X-Poolwatt-Signature: v1=<hex HMAC-SHA256>

каноническая строка = "v1." + timestamp + "." + METHOD + "." + path + "." + sha256(body)
секрет = секрет подписи ключа пункта
окно = 300 секунд
```

Для MQTT каноническая строка другая:
`"v1." + timestamp + ".MQTT." + topic + "."` + список `intervalStart:energyKwh`
через `;`, кВт·ч с тремя знаками.

### 2.3 Ключ оператора сети — касса, ERP сети

`POST /v1/charger-operators/{id}/price` — `Authorization: Bearer <ключ
оператора>`, задаёт цену сети за кВт·ч.

## Часть 3. API внешних поставщиков — задание подключающей стороне

Здесь перечислено всё, что мешает закрыть оставшиеся 14 историй ТЗ. Ни
одна из них не ждёт нашей работы — все ждут внешнюю сторону. Для каждого
поставщика: зачем, какие истории открывает, какой переключатель в
`src/lib/exchange/gates.ts` открывается, что нужно **от** поставщика и что
мы выставим **навстречу**.

Жёсткое правило, которое просим соблюдать и подключающую сторону: пока
поставщика нет, функция стоит за закрытым переключателем и отвечает 503.
Выдуманных IBAN, карт, результатов KYC, цен и лицензий в коде нет и быть
не должно — деньги, посланные на выдуманный IBAN, теряются.

### 3.1 EMI / банк-эмитент — IBAN и платежи

|               |                                                                                                             |
| ------------- | ----------------------------------------------------------------------------------------------------------- |
| Истории       | US-13 (личный расчётный счёт), US-16, US-22 (входящий перевод), US-07 (пополнение денежного баланса), US-19 |
| Переключатель | `ibansOpen` (`IBAN_PROVIDER`, сейчас только `sandbox` и только вне production)                              |
| Разделы ТЗ    | §19, §21, §24                                                                                               |

**Что нужно от поставщика:**

1. Выпуск IBAN на компанию и на физическое лицо. Запрос: идентификатор
   нашего клиента, тип владельца, страна, результат KYB/KYC. Ответ: IBAN,
   BIC, статус.
2. Выписка по счёту: `GET` с периодом, пагинация, остаток и список
   проводок с датой, суммой, контрагентом, назначением и собственным
   идентификатором проводки.
3. Исходящая выплата SEPA / SEPA Instant: получатель, IBAN, сумма,
   назначение, **наш ключ идемпотентности**, который поставщик обязан
   принять и уважать.
4. Статус выплаты и причина отказа отдельным полем, машиночитаемо.
5. Входящий перевод — вебхук.
6. Песочница с теми же кодами ошибок.

**Что выставим навстречу:** вебхук `POST /api/v1/webhooks/emi` —
зачисление, списание, смена статуса выплаты, смена статуса счёта. Подпись
запроса по тому же принципу, что у оборудования (HMAC-SHA256 от
канонической строки, окно 300 с), чтобы не вводить третью схему. Вебхук
обязан быть идемпотентен по идентификатору события поставщика.

**Чего не хватает кроме API:** лицензия EMI (литовская по юридическому
плану ЕС) и отдельное решение по Украине — литовская лицензия там не
действует, нужен банк-партнёр или лицензия НБУ.

### 3.2 Провайдер KYC — физические лица

|               |                                                               |
| ------------- | ------------------------------------------------------------- |
| Истории       | US-16; от него зависят переводы, счета и бронь                |
| Переключатель | отдельного нет — ступени §20 считаются по результату проверки |
| Разделы ТЗ    | §20, §23, §24                                                 |

**Что нужно:** создание проверки на человека и возврат ссылки на его
прохождение; вебхук с результатом (`APPROVED` / `REJECTED` / `REVIEW`) и
машиночитаемой причиной; уровень проверки (базовый / усиленный) — §20
различает ступени; повторная проверка при истечении срока; документы
проверки доступны по идентификатору, а не приходят нам в теле.

**Что выставим навстречу:** `POST /api/v1/webhooks/kyc`, подпись как в
3.1. Результат пишется в журнал append-only рядом с существующими
`ScreeningCheck` — перезаписать вердикт нельзя.

### 3.3 Провайдер KYB и санкционного скрининга — компании

|               |                             |
| ------------- | --------------------------- |
| Истории       | US-02 (уже закрыта вручную) |
| Переключатель | `KYB_PROVIDER` — закрыт     |
| Разделы ТЗ    | §4                          |

Сейчас оператор записывает свою проверку руками по национальному реестру
и сводным санкционным спискам, и критериям US-02 этого достаточно.
Автоматический путь — удобство, а не блокировка.

**Что нужно:** проверка компании по регистрационному номеру и стране;
структура ответа с бенефициарами; санкционный и PEP-скрининг по
названию и по бенефициарам; подписка на изменения (компания попала в
список после одобрения).

### 3.4 Процессинг карт и схема Visa/Mastercard

|               |                                                                                                                |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| Истории       | US-08 (оплата зарядки картой Poolwatt), US-14 (карты в дизайне партнёра), US-15 (оплата картой и баланс кВт·ч) |
| Переключатели | `cardTariffsOpen` (`CARD_TARIFFS_ENABLED`), `receiptRefundsOpen` (`RECEIPT_REFUNDS` + `PAYMENT_PROVIDER`)      |
| Разделы ТЗ    | §19, §53                                                                                                       |

**Что нужно:** выпуск виртуальной и физической карты на клиента; white
label — дизайн партнёра (US-14); авторизация с запасом и последующий
расчёт по факту — это ровно два момента §16.6, которые у нас уже так и
устроены; отмена авторизации; возврат (`refund`) с нашим ключом
идемпотентности; 3-D Secure / SCA; блокировка и перевыпуск; вебхук на
каждое событие авторизации и расчёта; **ставки интерчейнджа, выпуска и
обслуживания из договора** — их задаёт схема и передаёт EMI, выдумать их
нельзя, поэтому тарифы карт §53 стоят за закрытым переключателем.

**Что выставим навстречу:** `POST /api/v1/webhooks/cards`. Каждая
авторизация должна дойти до существующего водопада §16.6 и оставить чек
§46.

### 3.5 Мост OCPP — команда зарядной станции

|               |                                                                                     |
| ------------- | ----------------------------------------------------------------------------------- |
| Истории       | US-20 (частично работает без моста), US-30, §34 (бронь), §51 (команда от поддержки) |
| Переключатель | `ocppOpen` (`OCPP_BRIDGE_URL`)                                                      |
| Разделы ТЗ    | §23, §34, §51                                                                       |

Закрытый мост означает: оборудование отчитывается само (разделы 2.2), а
мы не делаем вид, что нажали кнопку на станции. Зарядку это не ломает —
водопад §16.6 работает без моста.

**Что нужно от сети зарядок:** OCPP 1.6J или 2.0.1, операции
`RemoteStartTransaction`, `RemoteStopTransaction`, `ReserveNow`,
`CancelReservation`, `UnlockConnector`, `TriggerMessage`; поток
`StatusNotification` и `MeterValues` — у нас это уже два метода из 2.2,
мосту остаётся их наполнить; формат QR действующей сети, чтобы
`GET /v1/points/resolve` понимал не только наш собственный код.

### 3.6 OCPI — роуминг с чужими сетями

|               |                                                              |
| ------------- | ------------------------------------------------------------ |
| Истории       | US-11 (расчёт готов, поток сессий от чужой сети — нет)       |
| Переключатель | отдельного нет; коридор создаёт оператор на `/admin/roaming` |
| Разделы ТЗ    | §8, §9.10, §24.2                                             |

Расчёт роуминга, курс «спот к споту», суточный предел и позиция партнёра
уже работают; каждый переход границы оставляет строку `RoamingSettlement`.
Чего нет: сессий от чужой сети и денежного перевода партнёру.

**Что нужно:** OCPI 2.2.1, модули `locations`, `cdrs`, `sessions`,
`tariffs`, `tokens`; `credentials`-рукопожатие; тарифы партнёра и
комиссия из договора; порядок закрытия периода и номер документа.

### 3.7 ENTSO-E — спотовые цены

|               |                                            |
| ------------- | ------------------------------------------ |
| Истории       | — (ломает коридор цены §6 и ступень §16.5) |
| Переключатель | `spotFeedOpen` (`ENTSOE_TOKEN`)            |
| Разделы ТЗ    | §6, §16.5, §18                             |

Код и страница оператора готовы. Токен бесплатный на
`transparency.entsoe.eu` — нужен только владелец, который его запросит,
плюс решение о первой торговой зоне и интервале (15 или 60 минут).
Закрытый переключатель означает, что зоны держат цену, которую оператор
поставил руками; он **никогда** не означает «нет коридора».

### 3.8 Выгрузка оператора сети (DSO) — полная сверка

|            |                                                      |
| ---------- | ---------------------------------------------------- |
| Истории    | — (§16.11 сверяется пока только по нашим показаниям) |
| Разделы ТЗ | §16.11                                               |

Для нас «данные сети» сейчас — показания, подписанные ключом объекта.
Суточный итог по объекту сделан так, чтобы выгрузку DSO можно было
поставить рядом. Нужен договор и доступ: формат выгрузки, период,
идентификатор точки поставки, транспорт.

### 3.9 Push — APNs и FCM

|               |                                               |
| ------------- | --------------------------------------------- |
| Истории       | US-29 (закрыта во всём, кроме push), US-08    |
| Переключатель | `pushOpen` (`APNS_KEY_ID` + `FCM_PROJECT_ID`) |
| Разделы ТЗ    | §25                                           |

Закрыто означает, что авария всё равно доходит письмом и на пульт станции;
это никогда не означает «авария потеряна».

**Что нужно:** ключ APNs (p8, Key ID, Team ID, bundle id приложения) и
сервисный аккаунт FCM; оба приложения зарегистрированы в своих магазинах
под теми же идентификаторами.

### 3.10 Агрегатор §16.7 — ликвидность вне книги

|               |                                          |
| ------------- | ---------------------------------------- |
| Истории       | — (ступень агрегатора в водопаде)        |
| Переключатель | `aggregatorOpen` (`AGGREGATOR_FALLBACK`) |
| Разделы ТЗ    | §16.7                                    |

Это не API, а **сторона с договором**: кто-то продаёт нам кВт·ч вне книги
и отвечает за поставку. Пока такой стороны нет, ступени агрегатора в
расчёте нет вовсе, и водителю честно говорят, что столько кВт·ч сейчас не
из чего дать. Нужно: контрагент, его цена и способ подтверждения сделки.

### 3.11 Автомобильные платформы

|            |                                                                          |
| ---------- | ------------------------------------------------------------------------ |
| Истории    | US-35, US-36, US-37 (CarPlay), US-38 (голос), US-39 (Android Automotive) |
| Разделы ТЗ | §39                                                                      |

**Что нужно:** разрешение Apple на entitlement CarPlay категории «EV
charging» (заявка от владельца, не от разработчика); проект Android
Automotive; API автопроизводителя для уровня заряда (US-39) — у каждого
производителя свой, и это отдельный договор на каждого.

Важно для планирования: CarPlay и Android Automotive **не** показывают
веб-страницу. Оболочка Capacitor туда не годится — нужен нативный экран,
а значит нативному клиенту нужны токены и методы API из разделов 0 и 1.18.

### 3.12 MQTT наружу — настоящие инверторы

Брокер сейчас слушает только `127.0.0.1`, и это безопасно: личность
объекта — ключ внутри сообщения. Чтобы принимать настоящие инверторы,
нужно: TLS на 8883, сертификат, отдельные учётные данные брокера на
объект и решение владельца открывать ли. Канонический формат подписи для
MQTT уже описан в 2.2.

### 3.13 Бухгалтерские форматы

Выгрузка §46 сделана по общедоступному описанию DATEV и BMD и отказывает,
пока партнёр не внёс свои номера счетов. Нужен диалект бухгалтера первого
живого партнёра — иначе формат проверен только на документации.

### 3.14 Что не поставщик, но тоже снаружи

- Заключение литовского юриста по переводам кВт·ч (§24.4) — открывает
  `transfersOpen` и US-19. Экран и подпись операции уже есть.
- Налоговое заключение по НДС (§46.7).
- Остальные заключения «Этапа 0» юридического плана ЕС.
- Значения X (коридор), Y (запас авторизации), комиссии, срок хранения
  кВт·ч (§18) — сейчас стоят условные.
- Реестр токенов: блокчейн или разрешённый реестр (§18). Сейчас — таблица
  Postgres.
- Публикация в App Store и Google Play: сейчас APK отдаётся с нашего
  домена, iOS — через TestFlight.

## Часть 4. Порядок подключения

Очередь не произвольная: одно открывает другое.

1. **Токены доступа к API** (раздел 0). Ни от кого снаружи не зависит,
   нужна всем новым фронтам. Делается нами.
2. **KYC** (3.2). Без него ступени §20 не поднимаются, а значит стоят
   счета, переводы и бронь.
3. **EMI / IBAN** (3.1). Открывает US-13, US-16, US-22, деньги в US-07.
4. **Процессинг карт** (3.4). Открывает US-08, US-14, US-15 и возвраты по
   чекам.
5. **ENTSO-E** (3.7) — дешёвое и быстрое, можно делать в любой момент
   параллельно.
6. **Push** (3.9) — тоже дешёвое, нужно до публикации в магазинах.
7. **Мост OCPP и OCPI** (3.5, 3.6). Нужны первые сети-партнёры.
8. **Автомобильные платформы** (3.11). Требуют и разрешения Apple, и
   нативного клиента, то есть идут после пункта 1.
